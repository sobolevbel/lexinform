Сними диагностику реального состояния бота: только чтение. Окно по умолчанию — 14 дней, если
в аргументах ($ARGUMENTS) не сказано иначе.

## Подготовка

```bash
git fetch -q origin state
git log --oneline -5 origin/state          # когда дамп писался последний раз
git show origin/state:lexinform.sql > /tmp/lexinform-state.sql
export LEXINFORM_DB_PATH=/tmp/lexinform-state.db
rm -f "$LEXINFORM_DB_PATH"
uv run lexinform db init && uv run lexinform db restore /tmp/lexinform-state.sql
uv run lexinform runs --days 14
uv run lexinform cost --days 14
gh run list --workflow daily.yml -L 10     # шли ли запуски и зелёные ли они
```

## Что проверить в базе

`sqlite3 "$LEXINFORM_DB_PATH"`, и сравни с тем, что должно быть по инвариантам:

- распределение `bills.status`; отдельно всё, что кончается на `_failed`, и всё с непустым
  `last_error` — с `analysis_attempts` (исчерпанный бюджет попыток сам не оживёт,
  нужен `reset`);
- `publications` по `status`: `pending` (оставленный упавшим прогоном — он никогда не
  дошлётся сам), `failed` (ретраится, но проверь `attempts` и `error`), `unknown`;
- отслеживаемые законопроекты: `discontinued_at IS NULL` и есть `sent`-карточка — сколько их,
  и нет ли среди них таких, где `last_checked_at` заметно отстал от остальных;
- законопроекты с карточкой, у которых `next_phase` уже ничего не даёт, но `is_over` ещё нет
  (акт с длинной вакацио легис) — карточка должна оставаться живой;
- бэклог реестра (`wykaz_backlog` в последних отчётах `runs`): растёт ли он;
- расписание: дневной прогон идёт по будням 05:23 и 16:23 UTC, в выходные 10:23, и GitHub
  стартует его на 3–4.5 часа позже — пропуск одного слота это норма, пропуск дня нет.

## Отчёт

Дай короткий дайджест (состояние на дату дампа, объём, сколько прогонов и во сколько обошлись),
затем список аномалий по убыванию важности — каждая с конкретной строкой/номером и командой,
которой чинится. Если всё чисто, так и скажи одной фразой, без пересказа цифр.
