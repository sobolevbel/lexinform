Проведи охоту на баги в lexinform. Это не код-ревью и не продуктовый аудит (для второго есть
`/product-review`): здесь ищутся дефекты реализации — потерянные и задвоенные новости, неверная
дедупликация, забытые ветки, состояния, из которых нет выхода. Главный прицел — **смены статусов
законопроекта и то, что об этом говорят посты**.

Каждый найденный дефект чинится сразу, с тестом, падающим на прежнем коде, и записывается в
реестр. Бюджет на вызовы модели — **$0**, если не сказано иного: вся машинерия статусов, постов,
фаз и дедупликации проверяется на gzip-текстах и JSON корпуса без единого запроса к API.

## Как готовиться

1. **`docs/BUGS.md`, раздел «Classes we have already had» — первым делом.** Почти каждый дефект,
   найденный здесь, оказывался вторым или третьим случаем формы, уже бывшей в истории: запасной
   вариант выбрал не тот файл, константная таблица недосчиталась члена, водяной знак использован
   как фильтр релевантности, последний элемент принят за представительный, пустота подменила
   «не читали». Возьми две-три формы и ищи их соседние случаи — это самый дешёвый способ найти
   настоящий баг.
2. Открытые записи того же файла — это невыясненные зацепки, а не находки. Проверить одну из них
   замером по корпусу — законный результат охоты, даже если она окажется пустой.
3. `CLAUDE.md`: инварианты, схема, факты об API. Там же сказано, какие измерения уже сделаны и
   какие варианты уже отвергнуты — не переоткрывай их без новых чисел.
4. `~/projects/lexinform-corpus/checks/README.md`, `FINDINGS.md`, `COLD.md` — **ради метода, а не
   только ради находок**. Раздел «Метод: что сработало здесь» стоит целого аудита.

## Метод: три яруса

1. **Реплей по корпусу.** 5 533 дерева стадий каденций 8–10, 938 печатей, 825 проектов RCL,
   4 387 заседаний комиссий, весь реестр RM. Продовый код получает сырые сохранённые ответы API.
   Harness — `checks/common.py`; запускать из чекаута `lexinform`:
   `uv run python ../lexinform-corpus/checks/NN_name.py`.
2. **Машина времени через `World`** (`tests/harness.py`). `World` собирает **настоящий**
   `Container`, а `FakePublisher` **и есть** продовый `RenderingPublisher` — значит лента постов,
   записанная пробником, это ровно то, что увидел бы читатель. Берёшь реальное дерево стадий из
   корпуса, подаёшь его по дням через `w.gateway.details[...]`, двигаешь `w.clock.current`,
   зовёшь `w.run()`. Так работают `31`–`33`; переиспользуй их каркас.
3. **Настоящий дамп прода** — `git show origin/state:lexinform.sql`. Для миграций, рендера по
   реальным данным и разбора отчётов прогонов (`runs.report_json` хранит их целиком).

## Правила, без которых числа врут

- **Невозможное число — сначала подозрение на пробник.** В этой охоте пробник врал дважды:
  `diff_stages` отдаёт уже плоский список, и прогон его через `stage_keys` считал детей дважды;
  а `detail` из корпуса несёт финальные `closureDate` и ELI, и подмешивать их к каждому дню
  значит объявить конец дороги в первый же прогон. Оба раза «находка» была моей ошибкой.
- **`World.publication()` зашит на каденцию 10.** Для каденций 8 и 9 спрашивай
  `w.repo.get_publication(term, number, ...)`, иначе они молча пропускаются — а именно там живут
  вето, Трибунал и отклонения Сената.
- **Цена правки меряется до правки.** Прежде чем менять правило, посчитай по корпусу, скольких
  строк это касается и во что обойдётся. Без числа правка не обсуждается.
- **Тест обязан падать на прежнем коде.** Порядок: сперва коммит теста и его падение, потом
  правка. `git stash` в этом репозитории общий между worktree — не пользуйся им для этого.
- **Правка, которая не меняет ни одного числа, не остаётся.** Перезапусти затронутые пробники
  после каждой правки: реплей ловит ту правку, которую ты только что внёс.
- **Удержанное — не потерянное.** Рамочная стадия ждёт следующего поста по замыслу. Считая
  потери, вычитай `list_held_status_changes`, иначе получишь два десятка ложных находок.

## Где искать

Смотри туда, где новое встречается с холодным.

- **Смены статусов и посты** — главное. `services/tracking/` целиком: дедупликация по
  `change_key` и `synthetic_key`, удержание и его выпуск, уникальные индексы публикаций,
  `Poster.record_change`/`tell`, рефрешер карточки. Спрашивай: может ли новость пропасть между
  «записали» и «рассказали»; может ли она уйти дважды; что будет, если прогон упал посередине;
  что будет, если стадии пришли не по порядку; что будет на повторном прогоне.
- **Асимметрии между путями.** `has_news` и `fills_in_the_past` применяются только на пути Сейма;
  RCL, wykaz, pre-print, rollover и linking постят всё. Один сосед перечитывает строку из базы,
  другой нет. Одна ветка пишет `skipped`-строку при `--no-publish`, соседняя не пишет. Каждая
  такая пара — кандидат.
- **Что приехало за последние дни** (`git log --since`). Новый код ещё никто не гонял по
  популяции.
- **Модули, которых нет ни в одном тесте по имени.** `services/sources.py`, `services/cost.py`,
  `services/lookup.py`, `models/ministries.py`, `services/tracking/stages.py`. Покрытие тут ни при
  чём: `pytest --cov` даёт 92 %, а дефекты были — код исполняется по фейкам, которые никогда не
  встречались с настоящей выдачей.

## Пробники

Лежат в `~/projects/lexinform-corpus/checks/`, отчёты — в `checks/out/`. Готовые:

- `31_tracker.py` — настоящий трекер по всем деревьям стадий, день за днём: потери, повторы,
  неотпущенные удержания, сходимость счётчиков.
- `32_idempotence.py` — тот же день дважды и день, прожитый без публикации.
- `33_order.py` — день, расщеплённый на два прогона: зависит ли лента от того, когда сработал cron.

Новый пробник — новый номер в том же блоке, с докстрокой, которая говорит, **какой вопрос** он
задаёт и почему этот вопрос не задавал никто раньше. Корпус не git-репозиторий: пробники в нём
не версионируются, поэтому вывод обязан быть самодостаточным.

## Что сделать с находками

На каждый подтверждённый дефект: число из пробника → тест (`tests/unit/` для чистой функции,
`tests/scenario/` для всего, что зовёт `World`) → правка → полный гейт
(`uv run pytest -q && uv run mypy && uv run ruff check src tests`, затем `ruff format`) → коммит.
Сообщение коммита английское, говорит **что было не так и на чём это измерено**.

Затем запись в `docs/BUGS.md`: в «Fixed» с числом «было/стало», либо в «Open», если правка
требует продуктового решения, а не патча — тогда напиши, какое именно решение нужно и почему
очевидный фикс неверен. Если находка — новый экземпляр уже известной формы, добавь её к этой
форме в последнем разделе; если форма новая, заведи её.

## Формат результата

1. Что найдено и починено — по одной строке на дефект, с числом.
2. Что найдено и оставлено открытым — с предложенной правкой и вопросом, который надо решить.
3. Что проверено и оказалось в порядке — это не менее ценно: срез, закрытый числом, не надо
   проверять снова.
4. Что пробовали и не сработало — чтобы следующая охота не повторяла.
5. Числа `CLAUDE.md`, разошедшиеся с корпусом.
