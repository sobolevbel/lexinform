# Compatible RCL multipart receipts and proposed commencement evidence

The new receipt profile accepts a complete map for two to five selected loose RCL parts.
It binds the actual frozen question and request to the ordered source selection. Each
part must resolve through the existing selection artifact and extraction links to an
exact whole leaf. The reader checks ranges, role, extent, hashes and the shared byte cap.
The database schema and single-part profile are unchanged. The new profile stores references, roles,
coordinates and checksums.

The default producer stays off. All 48 frozen profiles matched their preceding output.
Eighteen positive raw profiles supplied receipts through the local test path. The
repository saved and restored them exactly, with receipt sizes from 1,462 to 2,794 bytes.
Cached file-ID stubs cannot stand in for physical extraction parents. Readers of
single-part claim or content evidence treat the multipart profile as unknown.
[Raw reader qualification](rcl-reader-profiles.json).

The offline proposed-commencement check binds a scalar `effective_date` value to a
literal quote from the text of the project. It rejects an enacted-act role for this
profile. The pinned DOC example accepted its exact Article 5 quote and rejected a
duration mutation. Existing key-change and affected-group behavior is preserved.
This verifies the literal binding. Semantic support and actual legal commencement
remain separate questions. [Mechanical check](proposed-commencement.json).

The exact reader commit passed hosted CI and the relay transition, restart and timer
checks. [Release receipt](release.json).
