# Как редактировать документацию

Статус: актуальная инструкция · 24 сентября 2026.

## Запуск

Из корня репозитория:

```bash
make docs
```

Команда устанавливает нужные зависимости через `uv` и запускает Zensical.
Без Make: `uv run --frozen --group docs zensical serve`.

Откройте <http://127.0.0.1:8001>. Сохранение файла обновляет предпросмотр;
Ctrl+C завершает сервер. Интернет нужен для первой установки зависимостей,
затем страницы и поиск работают локально. Ключи и production state не нужны.

## Новая страница

1. Создайте Markdown в `docs/development/`, `docs/operations/`, `docs/reference/`
   или другом подходящем разделе. Начните с одного `# Заголовок`.
2. Для плана укажите дату и статус «план», для аудита — дату и проверенную версию.
   Для инструкции укажите дату содержательной проверки, если она действительно выполнена.
3. Добавьте страницу в `nav` файла `zensical.toml` и ссылку из тематического обзора.
4. Проверьте переходы и оглавление в браузере, затем выполните проверки ниже.

Пути старых страниц сохраняем, пока нет содержательной причины перемещать их.
У каждого правила один редактируемый источник. При переносе оставляйте указатель
и сохраняйте якоря, на которые уже ссылаются другие материалы.

## Ссылки, статусы и поиск

В Markdown ссылайтесь на исходники: `[Схема](reference/database.md)`.
Для кода вне `docs/` используйте GitHub URL; у исторического аудита предпочтителен commit.
Не ставьте `../src/` или ссылки на корневой README: этих файлов нет в сборке.
В самостоятельном HTML ссылка должна вести на готовый URL, например `../reference/database/`.

Используйте понятные статусы: «актуальная инструкция», «план», «исторический аудит»,
«заменён документом …». Не обновляйте дату проверки из-за исправления опечатки.
Заменённую страницу можно исключить из поиска, сохранив её доступной по ссылке:

```yaml
---
search:
  exclude: true
---
```

Интерфейс документации русский; отдельные элементы поиска могут оставаться английскими.
Корневые README, CONTRIBUTING и `web/README.md` читаются в редакторе или на GitHub,
а в локальный поиск не входят.

## Небольшая интерактивная вставка

Для раскрывающегося пояснения достаточно стандартного HTML — отдельная JS-сборка не нужна:

```html
<details class="doc-example">
  <summary>Почему ожидание batch входит в срок?</summary>
  <p>Читатель ждёт с момента постановки в очередь, а не с момента отправки провайдеру.</p>
</details>
```

<details class="doc-example">
  <summary>Почему ожидание batch входит в срок?</summary>
  <p>Читатель ждёт с момента постановки в очередь, а не с момента отправки провайдеру.</p>
</details>

Если нужен JS, положите его в `docs/assets/javascripts/`, подключите через `extra_javascript`
и запускайте только при наличии контейнера виджета. CSS ограничивайте классом виджета;
стили портала находятся в `docs/assets/stylesheets/extra.css`.
Добавьте текстовое объяснение, доступное поиску и читателю без взаимодействия.
Отдельный широкий шаблон пока не нужен: таблицы прокручиваются в общей оболочке.

## Самостоятельный HTML

Для нового прототипа используйте `docs/interactive/<name>/index.html` и соседние ресурсы.
Добавьте Markdown-страницу входа с описанием и статусом, включите её в меню.
В HTML поставьте ссылку возврата в портал. Используйте локальные ресурсы и системные шрифты.
Содержание HTML не предполагается доступным поиску: важные пояснения пишите на странице входа.

Не выключайте `use_directory_urls`: `legislative-process.md` и `legislative-process.html`
должны иметь разные адреса. Не раздавайте корень репозитория через HTTP.

## Проверка перед коммитом

```bash
make docs-check
```

Команда сначала собирает портал в строгом режиме, затем проверяет страницы,
ресурсы и якоря готового HTML, состав сборки
и наличие каждого исходного документа. Исключение для `href="#"` разрешено только
у исторического прототипа сайта. Внешние ссылки автоматически не обходятся.
Обязательный gate проекта остаётся в `CONTRIBUTING.md`.
