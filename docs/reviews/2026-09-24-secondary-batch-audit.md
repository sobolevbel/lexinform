отправки, неопределённый submit не повторяется автоматически, ответы и стоимость переживают
перезапуск. Однако расширение на вторичные сводки не доведено до той же надёжности.

## Что сделано хорошо

1. **Надёжная граница submit.** `BatchIntent` сохраняет готовый payload, модель, prompt version,
   резерв и время создания. `queued → submitting` коммитится и на ephemeral runner
   checkpoint'ится до запроса. Неопределённый ответ остаётся видимым оператору; это правильнее
   автоматического повтора с риском двойной оплаты.
2. **Отдельные уровни фиксации.** Получение результата, его применение к анализу/наблюдению и
   отправка Telegram не смешаны в одной сетевой транзакции. Memo + consumption записываются
   атомарно, стоимость подтверждается вместе с отчётом. Pending-before-send сохранён.
3. **Типизированные вопросы и общие адаптеры.** Дискриминированный `BatchQuestion`, группировка
   по виду и модели, разбор ожидаемой схемы, совместимость с legacy JSON и изоляция ошибок
   элементов позволяют расширять протокол без отдельных механизмов на каждый вид сводки.
4. **Secondary collection не меняет бизнес-статус билла.** Поздний digest не возвращает
   законопроект в публикацию и не отменяет операторское решение. Это чище, чем использовать
   `Bill.status` как состояние каждого фонового вычисления.
5. **Осмысленные проверки сбоев.** Есть тесты partial collection, restore, watermark,
   worker parity 1/4, позднего ответа, отказа чекпойнта, ручного обхода batch и dry run.
   Новые пробы дополняют их на границах подсистем.
6. **Ограниченный rollout.** Amendments остаются за production-гейтом; оценки экономии в плане
   явно названы историческими, а не новым замером. Это полезное ограничение риска.

## Подтверждённые проблемы

Номера и шкала совпадают с [реестром](../BUGS.md): P1 — потеря/существенная задержка новости,
P2 — неполное или вводящее в заблуждение сообщение, P3 — операторские/финансовые дефекты.
Финансовые P3 стоит исправить рано, несмотря на формальный ранг.

### B47 · P1 · ожидание сводки блокирует срочную информацию

`tracking/service.py::_detect` при `Waiting` выходит до сохранения стадий. Затем
`HearingReminder.remind` перечитывает из БД старые стадии. `window_closes_within` учитывает
только pilny и консультации, поэтому новое публичное слушание с дедлайном подачи заявок
сегодня не выводит законопроект из batch.

Проба: к опубликованному проекту одновременно приходят OSR и `PublicHearing` через десять
дней; по модели проекта срок заявок приходится на сегодня. Прогон ставит supplement в batch,
а `hearing_reminders == 0`, ошибок нет. Это доказанная задержка; пропуск самого окна зависит
от времени следующего запуска и ответа провайдера, его наличие в production не утверждается.

**Изменение:** принимать решение об ожидании по свежему наблюдению, включая даты слушаний,
актуальные agenda/decision deadlines. Если действие требуется скоро, завершать сводку
синхронно в пределах бюджета либо публиковать содержательную новость без неё. Не записывать
промежуточную стадию отдельно от её delivery work ради обхода теста: это сломает checkpoint.

### B50 · P1 · маркер не защищает от выхода из трекинга

`sqlite_repo.py::list_tracked` добавляет `awaiting_batch_since IS NOT NULL` только в условие
водяного знака. Предыдущее условие возраста закрытого проекта всё равно его исключает.

Проба: закрытый, не принятый проект ещё попадает в последний день настроенного grace period,
новая сводка ставится в batch. Через сутки ответ готов, но `tracked == 0`, обновления нет,
маркер остаётся. Полный проход использует тот же фильтр и сам по себе проблему не исправляет.
Это граничный случай, но он нарушает обещание завершить уже начатую доставку.

**Изменение:** учитывать ожидающую доставку отдельно от интереса к дальнейшему наблюдению.
Минимально — исключение для маркера в age predicate с сохранением правил linked/discontinued;
надёжнее — отдельная выборка незавершённой работы и явная политика её отмены при завершении
или переносе проекта. Проверить аналогичную границу entry-into-force/rollover отдельно.

### B48 · P2 · готовая сводка всё ещё зависит от повторного скачивания

`digest_supplement` сначала вызывает `_load_text`, затем строит контекст и memo key.
`DigestItemMeta` не сохраняет источник и связь результата с конкретным документом в форме,
которая позволяла бы закончить наблюдение без повторного чтения PDF.

Проба: поставить OSR в batch, завершить ответ, сделать dump/restore, создать новый Container,
убрать файл у источника. Сбор сохраняет правильный digest, но трекинг возвращает bare supplement,
публикует его без digest и записывает документ в `seen_supplements`. Оплаченная сводка потеряна
для читателя. Без нового Container проба проходила благодаря run-scoped `TextLoader` cache —
поэтому многократный `w.run()` не всегда моделирует реальные GitHub runners.

**Изменение:** сохранять связь ожидаемого наблюдения с memo key, документом и comparison
context. Для уже начатой работы применять сохранённый результат без повторного скачивания;
новую редакцию документа обрабатывать отдельно. Нельзя просто искать любой memo по URL:
один URL может начать отдавать другой текст. Для amendments проверить тот же путь.

### B49 · P2 · срок ожидания joint начинается заново

Memo key joint включает описания сравниваемых проектов. Изменилось описание — новый ключ —
новое задание со свежим `queued_at`. `may_wait_for_batch` и `awaiting_batch_since` ограничивают
трекинг, но не публикацию joint reply.

Проба: joint ждёт семь часов, у основного проекта обновляется summary. Следующий прогон
не выполняет fallback, а ставит второй batch; `joint_published == 0`. Повторение изменений
может повторять ожидание. Это не нарушение таймера отдельного job; это пробел плана:
дедлайн вычисления не равен дедлайну читательской доставки.

**Изменение:** хранить `first_wait_at`/deadline на устойчивой identity joint delivery
(term, bill, channel, kind), сохраняя его при смене контекста. После дедлайна — актуальный
синхронный ответ в пределах бюджета либо reply без сравнения. Не создавать Telegram
`pending` только ради хранения таймера: ещё не было попытки отправки.

### B45 · P3 · бюджетный отказ запускает более дорогой путь

В `_ask_or_wait` отказ `CostLedger.reserve` не возвращает отложенное состояние. Код доходит
до `sync_call()`, после которого лишь записывает фактическую стоимость. Та же ветка sync
не проверяет остаток бюджета при timeout/error fallback.

Проба: бюджет $0.001, fake batch reservation $0.1 — вызван синхронный joint. Отсутствие
intent здесь не означает отсутствие расходов. В существующем тесте
`test_secondary_reservation_over_budget_falls_back_without_an_intent` такое поведение даже
закреплено как ожидаемое. Значит, нужно изменить политику, а не просто добавить покрытие.

**Изменение:** бюджетный отказ — отдельный исход, например `DeferredBudget`, а не повод к sync.
Проверять бюджет перед любым платным fallback и корректно освобождать резерв заведомо
неотправленного job. Для необязательного joint разрешить bare reply; для документа — явно
решить, можно ли выпустить новость без сводки или сохранить работу до следующего запуска.
Добавить причину в отчёт, чтобы оператор отличал нехватку бюджета от ожидания провайдера.

### B46 · P3 · выключатель не действует на сохранённую очередь

`submit_queued_batches` не проверяет `submit_batches` или текущий `batch_kinds` и отправляет
все queued intents. Отключение работает лишь косвенно, если до submit обычный проход дошёл
до того же memo key, получил синхронный ответ и удалил intent. При пропущенной/упавшей фазе
или ненужном больше контексте эта защита не срабатывает.

Проба в двух вариантах: создать queued joint, новый Container с `enabled=false` либо без
`joint` в kinds, вызвать submit. В обоих случаях provider получает запрос. Открытые/uncertain
задания — другая категория: их действительно нужно продолжать сверять и собирать.

**Изменение:** проверять разрешение отправки на её фактической границе. Для known-unsubmitted
intent определить политику cancel/hold и освобождения резерва. Не удалять `submitting/open`
при выключении и не переставлять готовый payload на другого провайдера. Добавить сценарий
pipeline с отказом tracking до фазы submit, а не ограничиваться прямым вызовом сервиса.

## Архитектурные риски и улучшения без подтверждённого инцидента

- **У batch сейчас две модели ожидания.** Первичный/reanalysis использует bill status,
  generation и ReadyAnalysis, secondary — memo key и частично bill marker. Объединять
  бизнес-семантику насильно не нужно, но общий transport lifecycle стоит выделить из
  разросшегося `AnalysisService` после исправления дефектов. Политика применения должна
  оставаться у анализа, трекинга и публикации.
- **Memo — кэш результата, а не вся модель работы.** Он хорош для дедупликации, но не хранит
  устойчивую читательскую identity, отмену и deadline. B48/B49 — два следствия этого пробела.
  Нужен небольшой persisted continuation с identity/context/result key, не новая универсальная
  task-платформа.
- **Poller не знает локальную очередь.** Он смотрит активного провайдера целиком; Anthropic
  ended из другой программы может вызывать лишние dispatch, OpenAI смотрит только completed
  в 40-минутном окне. При длительном простое, смене provider или failed/expired событии
  ускоренного запуска может не быть. Это прочитанные ветви кода, не проверка состояния VPS.
  Нужны reconciliation по owned IDs и запуск обработки просроченных ожиданий независимо от
  появления completed batch. Шесть часов — порог следующего run, не гарантированная доставка.
- **Snapshot/сканы раздувают state.** Пока intent queued/submitting, контекст со scan.data и
  подготовленный payload одновременно содержат base64. Git checkpoint записывает это в
  историю SQL-дампа. При нынешнем объёме проблема не измерена; стоит замерить размер dump и
  время checkpoint на нескольких крупных сканах до введения отдельного blob store.
- **Типы можно сузить.** `LlmBatch.call_kind` допускает весь CallKind, включая triage,
  а answer/meta — независимые union. Внешние данные проверяются адаптерами и consume, однако
  контракт допускает невозможные комбинации. BatchKind и типизированные success/error
  envelopes уменьшат число динамических проверок. Это улучшение, не найденная потеря данных.
- **Тестовый процесс маскирует рестарты.** Нужно систематически применять новый Container
  между enqueue, collect и delivery, а не только `restore` в том же объекте. Отдельный тест
  с новым TextLoader оказался существенно сильнее прежнего restore-теста.

## Оценка плана

Согласен с типизированным контрактом, durable intents, memo reuse для сканов, атомарным
чекпойнтом наблюдения, ручным sync и поэтапным rollout. Не согласен с безусловным «весь пост
ждёт сводку»: оно конфликтует с продуктовым приоритетом своевременных действий. Для дедлайнов
нужен явный escape path, не только urgency по метаданным законопроекта.

План ограничил ожидание job и наблюдения в tracking, но пропустил deadline joint delivery,
сохранённую связь с источником для применения результата и правила budget fallback.
Формулировка про выключение также сильнее фактического поведения сохранённой очереди.
Эти пункты нужно добавить в acceptance criteria до заявления о завершённой архитектуре.

Историческая оценка самого плана — около $6.7 экономии за каденцию — не оправдывает крупного
переписывания системы ради secondary. Это не новый расчёт. Здесь важнее убрать риски потери
новости и сохранить простую модель; дополнительные framework-абстракции вторичны.

## Конкретная последовательность изменений

1. **B47:** decision-to-wait по свежему наблюдению и всем близким actionable deadlines;
   тест hearing + OSR и границы суток. Новость не задерживается необязательной сводкой.
2. **B50:** очередь незавершённой доставки переживает age cutoff; отдельная политика
   linked/discontinued/rollover. Готовый ответ заканчивается доставкой либо явной отменой.
3. **B45 + B46:** единая политика admission и kill switch непосредственно перед submit/sync;
   тесты exhausted budget, timeout fallback, отключённой очереди и отказа tracking.
4. **B48:** persisted source/context → memo reference для вторичных работ; новый Container,
   недоступный PDF, изменившийся URL/content и бесплатное повторное применение.
5. **B49:** неизменный первый deadline joint delivery; смена summary/group не продлевает
   ожидание, поздние ответы не создают повторной публикации.
6. **Проверка после исправлений:** снять strict-xfail только с реально исправленных проб;
   полный gate, cold-restart сценарии, существующие тесты обоих адаптеров. Повторять платный
   smoke имеет смысл только при изменении payload/parser, не вместо тестов состояния.
7. **Rollout:** сначала joint, затем supplement после устранения потерь, amendments после
   исходного production-гейта ≥10 завершённых batch, p90 ≤2 ч и проверенного poller.
   Наблюдать также время от first_wait до reader delivery, а не только provider completion.

Каждый пункт — отдельный проверяемый коммит либо несколько небольших коммитов. В этом аудите
runtime-код не исправлялся: сохранены отчёт, реестр и исполняемые критерии будущих исправлений.
