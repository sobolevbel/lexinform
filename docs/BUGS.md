## Как пользоваться

Текущие баги сгруппированы по статусу, внутри группы — по влиянию на читателя.
Номера B1…B96 постоянные:
старые обозначения `#4` и `B4` означают одну запись.
`open` — воспроизведённый дефект; `candidate` — ещё не доказанная гипотеза.
`deferred` — подтверждённый дефект, отложенный по решению владельца;
`fixed locally` — код исправлен и проверен локально, production ещё не подтверждён.
Закрытие требует регрессии, падающей до исправления и проходящей после него,
либо документированного результата расследования без изменения кода.

| Приоритет | Влияние |
| --- | --- |
| P0 | Ложное утверждение в канале или безвозвратная потеря законопроекта |
| P1 | Потерянная или повторная новость, восстановимая вручную |
| P2 | Формально верное, но неполное или вводящее в заблуждение сообщение |
| P3 | Ошибка оператора, отчёта или затрат без прямого влияния на читателя |

P3 не означает, что расходы можно игнорировать: порядок инженерных работ может учитывать стоимость.
Исправления и отклонённые гипотезы — в [архиве](archive/bugs.md);
[повторяющиеся ошибки](development/failure-patterns.md) — памятка для аудита.

### B91

**P1 · fixed locally · найден 14.10.2026.** `services/digest.py::_resume_parts`, `_send_parts`.

После трёх подтверждённых отказов первой или промежуточной части дайджеста следующая
queued часть снова выбирает всю цепочку для отправки. `_send_parts` не проверяет
attempts каждого участника и повторяет исчерпавшую лимит часть. Неизменный отказ
может удерживать `_resume_parts` перед созданием следующего недельного draft.
Без queued хвоста последняя failed часть с тремя попытками корректно не выбирается:
поведение зависит от позиции части, хотя лимит относится к физической отправке.

Регрессия: `test_digest_resume_respects_each_physical_parts_attempt_limit`;
две позиции падают с `--runxfail`, контроль последней части проходит.
Приёмка: проверять лимит каждой физической части и не обходить его через очередь
соседнего участника; повторная ручная публикация не должна молча сбрасывать лимит.
Оператор должен видеть причину остановки и иметь явный путь восстановления.

Исправлено локально 14.10.2026: Каждая физическая часть проверяет свой лимит; цепочка с исчерпанной частью
не блокирует следующий draft. Ручной `/digest publish` лимит не сбрасывает.
Явный `/delivery ID retry` для failed части дайджеста с тремя попытками
сбрасывает только её лимит с записью в аудит.

### B92

**P1 · fixed locally · найден 14.10.2026.** `services/digest.py::_resume_parts`,
`adapters/sqlite_repo.py::resolve_delivery`.

`/delivery PART dismiss REASON` первой или промежуточной unknown части дайджеста
закрывает только эту часть. Следующие части остаются queued, но `_resume_parts`
отвергает любую цепочку с dismissed участником. Закреплённые за хвостом digest-only
источники остаются queued и исключаются из будущих подборок. `/delivery` не разрешает
queued запись, поэтому для хвоста нет доступного оператору пути завершения.

Регрессия: `test_resolving_a_digest_part_leaves_no_unrecoverable_tail`;
dismiss первой и промежуточной частей падают, confirm/retry обеих позиций проходят.
Приёмка: явно определить семантику dismiss физической части. Либо оставшиеся части
доставляются с сохранённым составом, либо хвост и только его источники атомарно
закрываются как dismissed. Уже подтверждённые события остаются sent; membership
и аудит сохраняются, повторное назначение события другой части запрещено.

Исправлено локально 14.10.2026: Dismiss атомарно закрывает ещё не начатый хвост и принадлежащие ему
digest-only источники как dismissed. Sent события, membership и payload сохраняются;
аудит решения доступен по ID каждой закрытой физической части.

### B93

**P2 · fixed locally · найден 14.10.2026.** `services/message_parts.py::freeze_parts`,
`adapters/sqlite_repo.py::resolve_delivery`.

Поглощённый суточный статус хранит `absorbed_by`, а его held-change ID переносится
в последнюю физическую часть нового сообщения. Dismiss раннего unknown продолжения
закрывает queued потомков, но не применяет их эффекты закрытия к поглощённой записи.
Она остаётся queued, retry её пропускает по absorbed_by. Dismiss непосредственно
последней части корректно закрывает эту запись, то есть результат зависит от позиции.

Регрессия: `test_dismissed_continuation_finishes_its_absorbed_change`;
раннее продолжение падает, последняя часть проходит, оба случая переживают restore.
Приёмка: завершать принадлежащие закрываемому хвосту поглощённые записи как dismissed
в той же транзакции. Не выдавать их за доставленные и не затрагивать чужие held IDs.

Исправлено локально 14.10.2026: При dismiss раннего продолжения эффекты закрытия применяются ко всему
неотправленному хвосту. Поглощённые записи закрываются только при совпадении
absorbed_by с владельцем закрываемой цепочки.

### B88

**P3 · fixed locally · найден 14.10.2026.** `.github/workflows/daily.yml`,
шаг `Tell the log channel when the job failed around the run`.

При ошибке pipeline общий alert всегда добавляет `the state may be unsaved`,
даже когда `restore: success` и `dump/push: success`. В прогоне 243 dump завершился,
state commit `bd11016` успешно запушен; восстановленная копия содержит run 243
и его batch-результаты. Предупреждение о риске несохранённого состояния здесь вводит
оператора в заблуждение и смешивает частичный сбой разборов с отказом сохранения базы.

Доказательство: [лог прогона 243](https://github.com/sobolevbel/lexinform/actions/runs/38555234804),
шаг `Dump database and push state branch`, успешный push в 11:25:41 UTC.

Приёмка: текст alert зависит от исхода dump/push; при успехе сообщает, что состояние
сохранено, при failure/skipped/неизвестном исходе отражает соответствующую неопределённость.
Проверить частичную ошибку pipeline с успешным сохранением и отдельный сбой dump/push.

Исправлено локально 14.10.2026: alert использует исход `steps.dump.outcome`.
При `success` сообщает `state saved successfully`; при `failure` — отказ сохранения,
при `skipped` — пропуск, при пустом или неизвестном исходе — отсутствие подтверждения.
Регрессия `test_failure_alert_reports_the_actual_state_save_outcome` запускает настоящий
shell-блок workflow с подставным `curl`: все четыре случая падали до исправления
и проходят после него. Удаление служебного сообщения relay сохраняется.
Production alert после выкладки в этой проверке не наблюдался.

### B86

**P1 · deferred · найден 14.10.2026.** `services/analysis.py::request_document_review`,
`services/document_reviews.py::DocumentReviewService`.

`SECONDARY_BATCH_SUBMISSIONS=2` ограничивает число отправок одного review context

## B4

**P1 · fixed · найден 16.09, исправлен 25.09.2026.**

Неопределённая доставка не отправляется повторно автоматически: это действующее правило
защиты от дублей, а не подтверждённая ошибка. Старые `pending` становятся `unknown`,

без отправки. Старые записи без полного payload нельзя повторить. Смена статуса и аудит атомарны;
подтверждение освобождает только включённые held-change IDs. ID публикации не переиспользуется.

повторные команды, изменённые факты и родитель, старые записи, dry run, rollback аудита,
закрытие карточки и точное освобождение удержанных событий. Миграция v34 проверена на копии
свежего state dump; production не изменялся. [Порядок восстановления](operator-commands.md#recovering-an-uncertain-delivery).
Случай `--no-publish` закрыт отдельно в B22: queued-доставка повторяется.
