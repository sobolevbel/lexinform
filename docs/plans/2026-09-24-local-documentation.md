# Локальный портал документации lexinform

Дата: 24 сентября 2026. Статус: реализован; результаты и границы проверки ниже.

## Результат реализации · 24 сентября 2026

Вход: [главная портала](../index.md). Запуск:
`uv run --frozen --group docs zensical serve`, адрес <http://127.0.0.1:8001>.
Редактирование и проверки описаны в [инструкции автору](../authoring.md).

| Этап | Результат |
| --- | --- |
| DOC-01 | Zensical 0.0.64 на Python 3.14.7; техническая проба во временном каталоге, затем проверка полного корпуса |
| DOC-02 | Группа docs и lock, явное меню, тематические входы, локальный сервер, README/CONTRIBUTING |
| DOC-03 | Инструкция автору, HTML-пример раскрывающегося пояснения, локальные стили и системные шрифты |
| DOC-04 | Открытые баги отделены от архива; roadmap очищен; §25 сайта перенесён в четыре тематические страницы с сохранением прежних якорей; устаревшая схема отмечена |
| DOC-05 | Отдельная задача CI, строгая сборка и проверка готовых HTML-ссылок, якорей, ресурсов и состава сборки; регрессии проверяющего скрипта |

Проверено локально:

- Строгая сборка, включая запуск `--offline`, проходит без приложения, ключей и production state.
- В отдельное пустое окружение установлена только группа docs по lock; сборка полного корпуса
  и проверяющий скрипт проходят без зависимостей бота и web. Сервер остановлен через Ctrl+C.
- В браузере открыты главная и три самостоятельных HTML; их ссылки возврата присутствуют.
- Поиск: `awaiting_batch_since` находит схему и архитектуру; `миграции` — справочник БД;
  `консультации` и `wysłuchanie` — соответствующие гайды; `RCL` — эксплуатацию и scraper;
  `B50` — исправленную запись в архиве. Внутренний интерфейс поиска частично английский.
- На временных страницах проверены добавление и автоматическое обновление Markdown,
  HTML и CSS; после удаления проб чистая сборка их не содержит.
- В копии сборки намеренно сломанная HTML-ссылка вызывает ошибку проверки;
  в копии исходников сломанная Markdown-ссылка останавливает strict build.
- Полный pytest, strict mypy и Ruff проходят. Шесть существующих xfail относятся к открытым
  secondary-batch дефектам; перенос документации их не исправляет.

Границы: отдельная проверка мобильного viewport и полный клавиатурный обход пока не завершены.
Поиск открывался с клавиатурным вводом и закрывался Escape. Содержательная юридическая сверка
и обновление старой HTML-схемы не выполнялись; их даты и ограничения явно указаны.
Публикация портала в интернет не настроена. Нижележащие разделы сохраняют исходный план.

## 1. Решение

Использовать **Zensical**, стандартный генератор статической документации, с исходниками
в Git и запуском через существующий `uv`. Обычные страницы редактируются в Markdown,
нестандартные — в HTML/CSS/JS. Браузер автоматически обновляется после сохранения файла.
Основное требование владельца: документацию должно быть удобно редактировать именно в файлах.

Генератор отвечает за навигацию, оформление, оглавление, поиск и локальный сервер.
Собственная разработка ограничивается оформлением отдельных страниц и проверками документации.
Редактор в браузере, CMS, база данных и отдельный backend для этой задачи не нужны.

Это внутренний портал проекта. Публичный сайт `web/` на Django/Wagtail развивается отдельно;
его запуск, PostgreSQL, секреты и production state не требуются для чтения документации.
Гайды читателям можно просматривать здесь, но это не означает их публикацию на lexinform.pl.

## 2. Что обнаружено в репозитории

Инвентаризация выполнена по рабочему дереву, а не по старым планам:

- В `docs/` 28 файлов: 25 Markdown и 3 HTML до добавления этого плана.
- Дополнительные точки входа: `README.md`, `CONTRIBUTING.md`, `web/README.md`.
- Есть инструкции, технические справочники, продуктовые материалы, планы и датированные аудиты.
  Они лежат рядом, но отличаются по назначению и степени актуальности.
- Таблица Documentation в корневом README перечисляет только часть материалов.
- `website-development-plan.md` занимает 2281 строку; поздние ревизии дополняют и исправляют
  ранние разделы. Поисковая выдача без указания статуса может отправлять к старому решению.
- `database.html` описывает «Пять таблиц», тогда как `MIGRATIONS` уже создаёт, среди прочего,
  `analysis_memo`, `llm_batches`, `llm_batch_items`, `llm_batch_intents`.
  Размещение HTML на портале само по себе не сделает схему актуальной.
- `database.html`, `legislative-process.html`, `plans/website-design-prototype.html` имеют
  самостоятельный дизайн; первые две страницы загружают шрифты с Google Fonts.
- В `pyproject.toml` есть `uv` workspace и группа `dev`; отдельной группы документации,
  генератора сайта и docs-проверки в CI пока нет.

Организационная задача важнее смены формата: дать понятную точку входа, отделить действующие
правила от истории и сохранить существующие адреса файлов.

## 3. Сравнение решений

| Решение | Соответствие задаче | Решение для lexinform |
|---|---|---|
| Zensical | Markdown, Python/uv, встроенные сервер и поиск, CSS/JS и собственные шаблоны | Выбран: минимально меняет рабочий процесс |
| MkDocs + Material | Привычный стек для Python-документации | Не начинать новый портал на теме в maintenance mode |
| Astro Starlight | Хорошо подходит для Markdown/MDX и сложных кастомных страниц | Резерв, если нужны многочисленные компоненты: сейчас добавит Node и второй менеджер зависимостей |
| Sphinx | Уместен для большого API-справочника и сложных перекрёстных ссылок | Основная масса наших текстов — инструкции и планы; его возможности сейчас не определяют выбор |
| Django/Wagtail | Уже присутствует в публичном сайте | Избыточные зависимости для просмотра файлов; смешает документацию и редакционный продукт |
| Собственный сервер Markdown | Можно точно подогнать под себя | Придётся поддерживать поиск, ссылки, оглавление, обновление и оформление |

Material for MkDocs официально переведён в maintenance mode в связи с переходом команды
на Zensical. Точную дату завершения поддержки не используем как опору решения: объявление
обновлялось. [Объявление команды](https://squidfunk.github.io/mkdocs-material/blog/2025/11/11/insiders-now-free-for-everyone/).

Zensical устанавливается как Python-пакет и документирует работу через `uv`.
[Установка](https://zensical.org/docs/get-started/).
Starlight поддерживает отдельные Astro/HTML-страницы и общий компонент оформления:
это подходящий запасной вариант, если документация превратится в набор интерактивных приложений.
[Кастомные страницы Starlight](https://starlight.astro.build/guides/pages/).

Выбор Zensical окончательный для первого этапа; перед основной миграцией нужен небольшой
технический прогон на наших файлах. Совместимость установленного релиза с Python 3.14,
HTML и существующими ссылками в рамках этого планирования ещё не проверялась.

## 4. Навигация: сначала смысл, потом перемещения

В первой версии существующие файлы остаются на местах. Меню задаётся явно в `zensical.toml`;
название раздела не обязано совпадать с именем каталога.

| Раздел меню | Материалы |
|---|---|
| Начало | Новая главная `docs/index.md`, обзор проекта, как читать и редактировать документацию |
| Разработка и архитектура | `process-plans.md`, `text-selection.md`, `rcl-scraping.md`, `state-retention.md`, вход в инструкции разработчика |
| Эксплуатация | `operator-commands.md`, `rcl-proxy.md`, `llm-cost.md` |
| Предметная область | `legislative-process.md`, ссылка на визуальную карту процесса |
| База данных | Новая Markdown-страница о схеме, ссылка на существующую HTML-визуализацию |
| Гайды читателям | `guides/README.md` и пять гайдов; явная пометка о назначении материалов |
| Публичный сайт | Текущий статус разработки, концепция, прототип и ссылки на план |
| Планы и решения | `roadmap.md`, `plans/`, включая монетизацию и этот план |
| Аудиты и инциденты | `reviews/`, `incident-2111.md`; документы показывают дату и контекст проверки |
| Реестр дефектов | `BUGS.md`, отдельный заметный пункт |

Главная должна отвечать на задачи: «запустить проект», «разобраться в обработке законопроекта»,
«проверить эксплуатацию», «найти план», «добавить страницу». Краткое назначение рядом со ссылкой
полезнее каталога всех заголовков. Для длинных документов включить оглавление текущей страницы.

Новые тематические инструкции постепенно размещать в `docs/development/`, `docs/operations/`
и `docs/reference/`. Старые файлы переносить только при содержательной переработке, с отдельной
проверкой ссылок в README, AGENTS, CLAUDE, skills и других документах. Массовое переименование
ради красивого дерева не входит в первый этап.

## 5. Файлы и запуск

Предлагаемая структура добавлений:

```text
zensical.toml
pyproject.toml                  # отдельная dependency-group docs
uv.lock
docs/
  index.md
  authoring.md                 # короткая инструкция автору
  reference/database.md         # актуальность схемы и вход в визуализацию
  development/index.md
  operations/index.md
  plans/index.md
  reviews/index.md
  assets/stylesheets/extra.css
  assets/javascripts/           # только когда появится конкретный виджет
docs-theme/
  wide.html                    # при необходимости широкого макета
site/                          # результат сборки, не коммитится
```

`docs_dir` — только `docs`, `site_dir` — `site`. Не раздавать корень репозитория через
`python -m http.server`: там находятся служебные файлы и `.env`.
Генератор не должен читать настройки приложения или подключаться к его сервисам.
В `.gitignore` добавить `site/` и фактический каталог кеша выбранного релиза.

Зависимость добавить в группу `docs`, зафиксировать разрешённую версию в `uv.lock`.
Не устанавливать инструменты документации в production-зависимости бота. При реализации
проверить существующий CI с `--all-groups`: он тоже начнёт устанавливать эту группу.

Целевые команды после реализации:

```bash
uv sync --frozen --group docs
uv run --frozen --group docs zensical serve --dev-addr 127.0.0.1:8001
uv run --frozen --group docs zensical build --strict
```

Порт 8001 выбран, чтобы не мешать обычному Django runserver на 8000.
Настроить его также через `dev_addr`, тогда ежедневная команда сокращается до
`uv run --frozen --group docs zensical serve`.
Сервер запускается вручную и завершается Ctrl+C; автозапуск как системная служба не нужен.
Предпросмотр с обновлением описан в [документации serve](https://zensical.org/docs/usage/preview/),
сборка и строгий режим — в [документации build](https://zensical.org/docs/usage/build/).

Начальная конфигурация должна быть небольшой: имя сайта, каталоги, адрес, явное меню,
русский язык интерфейса и локальные стили. Сохранить английские технические тексты и польские
названия; перевод всего корпуса не является условием запуска.
Не включать мгновенную SPA-навигацию на первом этапе: обычные переходы проще для кастомного JS.

## 6. Как добавлять и редактировать страницы

### Обычный текст

1. Создать `.md` в тематическом каталоге, начать с `# Заголовок`.
2. Написать обычный Markdown: ссылки, списки, таблицы и блоки кода.
3. Добавить страницу в меню и ссылку с подходящей обзорной страницы.
4. Сохранить файл, проверить обновившуюся страницу и выполнить строгую сборку.

Никакой обязательной схемы из десятка полей. Для плана или аудита под заголовком указывать
дату и статус обычным текстом, видимым и на GitHub. Front matter нужен для специальных
настроек, например выбора шаблона. Код и терминальные команды должны копироваться как текст.

### Небольшой виджет в обычной статье

Markdown остаётся основным содержанием; HTML-контейнер, CSS и JS добавляют интерактивную часть.
Стили ограничивать классом виджета. JS запускать только при наличии его контейнера.
У диаграммы или калькулятора должно быть краткое текстовое объяснение для поиска и доступности.
Не вводить React/Vue или отдельную сборку JS ради одного переключателя.

### Страница со своим макетом в общей оболочке

Использовать шаблон `docs-theme/wide.html`, подключённый через `theme.custom_dir`, и
`template: wide.html` в front matter страницы. Сохранить поиск и боковое меню, расширив
контентную область. Zensical поддерживает собственные шаблоны на MiniJinja, CSS и JS;
это не полная взаимозаменяемость с Python Jinja. [Customization](https://zensical.org/docs/customization/).

### Полностью самостоятельная HTML-страница

Существующие три HTML сохранить с их оформлением и путями. Предусмотреть Markdown-страницы
входа с описанием, статусом актуальности и ссылкой «Открыть визуализацию»; они попадут в меню
и поиск. Самостоятельный HTML должен открываться отдельной страницей без iframe по умолчанию.
Добавить в него ссылку возврата к документации. Копирование HTML и ресурсов проверить на
первом техническом прогоне; не предполагать, что его содержимое индексируется как Markdown.

Для новых подобных страниц использовать `docs/interactive/<name>/index.html` и соседние ресурсы.
Общая оболочка предпочтительна для справочников, самостоятельный HTML — для прототипов
и больших визуальных схем. Не переписывать существующий дизайн только ради единообразия.

## 7. Корневые документы, ссылки и поиск

`README.md`, `CONTRIBUTING.md`, `web/README.md` на первом этапе остаются каноническими файлами
на своих местах. Обзорные страницы портала дают ссылки на них в GitHub и называют локальный путь.
Это явное ограничение первой версии: их полный текст не будет доступен в локальном поиске
и офлайн-просмотре. Весь текущий корпус `docs/` должен быть доступен локально.

На следующем этапе вынести подробные инструкции из CONTRIBUTING в `docs/development/`
по темам «установка», «тесты», «миграции», «эксплуатационные проверки». В CONTRIBUTING оставить
короткий запуск, обязательный gate и ссылки. Аналогично переносить подробности README только
при реальной редактуре. У каждого содержательного раздела один редактируемый источник;
ручные копии, symlink-ферма и собственный конвертер ссылок не нужны.

В Markdown использовать относительные ссылки на `.md` и ресурсы. Отдельно проверить переходы
между каталогами, якоря кириллических заголовков и ссылки на исходный код вне `docs/`:
для последних использовать адрес GitHub. Исторические аудиты по возможности связывать с commit,
актуальные инструкции — с текущими исходниками. Не считать успешную сборку доказательством
исправности всех ссылок внутри сырого HTML.

Оставить `use_directory_urls = true`: соседние `legislative-process.md` и
`legislative-process.html` должны давать разные адреса (`/legislative-process/` и
`/legislative-process.html`). Вариант плоских URL создаёт здесь конфликт имён.

Поиск работает на стороне браузера; внешний сервис не нужен.
Документация Zensical заявляет многоязычный поиск, но отдельно отмечает английский интерфейс
самого поиска. Не обещать полностью русский UI без проверки выбранного релиза.
[Site search](https://zensical.org/docs/setup/search/).
Приёмочные запросы: `awaiting_batch_since`, `миграции`, `консультации`,
`wysłuchanie`, `RCL`, `B50`. Проверять подходящие страницы, а не только непустую выдачу.

Архивные планы и аудиты должны иметь явные заголовки со статусом/датой. Устаревшие версии
планов исключать из поиска при наличии актуальной замены, сохраняя ссылки из истории.
Не исключать все аудиты: они содержат полезные объяснения причин решений.

## 8. Актуальность и единый источник истины

Для документов ввести четыре понятных статуса: «актуальная инструкция», «план»,
«исторический аудит», «заменён документом …». Для изменяемого справочника указывать дату
последней содержательной проверки; не обновлять её автоматически при косметических правках.

Первая редакционная очередь:

1. `database.html`: пометить как устаревший снимок до сверки с текущими миграциями.
   На Markdown-странице схемы дать ссылку на `MIGRATIONS` как источник истины.
2. `website-development-plan.md`: сделать короткий индекс действующих решений и показать,
   какие поздние разделы заменяют ранние. Затем вынести действующую спецификацию в отдельные
   тематические документы; старый план оставить историей с устойчивыми якорями.
3. `roadmap.md`: отделить открытые задачи от уже завершённых сведений; реестр багов остаётся
   в `BUGS.md`, состояние реализации сайта — в `website-implementation-progress.md`.
4. Для двух описаний законодательного процесса указать аудитории и согласованную дату проверки;
   технический справочник и визуальная читательская версия не обязаны быть буквальными копиями.

Позже можно генерировать таблицы схемы из пустой временной SQLite после применения миграций,
сохранив поясняющий текст вручную. Это отдельное улучшение, не условие запуска портала.
Ни сборка документации, ни проверка схемы не должны требовать production-дампа или LLM.

## 9. Этапы и критерии готовности

| Этап | Изменения | Проверяемый результат |
|---|---|---|
| DOC-01: технический прогон | Zensical на Python 3.14; копия нескольких наших Markdown, все три HTML, ссылки и поиск | Установка, build, serve и обновление работают; адреса HTML/Markdown не конфликтуют |
| DOC-02: первый полезный портал | Группа docs, lock, конфиг, главная, меню, страницы входа, ignore, команда в CONTRIBUTING | Весь `docs/` доступен через один локальный адрес; обычная правка текста сразу видна |
| DOC-03: удобство автора | `authoring.md`, пример виджета, при необходимости широкий шаблон, локальные ресурсы | Новую Markdown-страницу и самостоятельный HTML можно добавить по короткой инструкции |
| DOC-04: достоверность | Пометки устаревших материалов, индекс действующего плана сайта, тематические инструкции | Текущие правила различимы с историей, содержательные копии не расходятся |
| DOC-05: постоянная проверка | Отдельная docs-задача CI, проверка внутренних ссылок и состава сборки | Сломанная ссылка или пропавшая страница даёт понятную ошибку до слияния |

DOC-01 проводить во временном каталоге, без изменения исходных документов. Если обнаружится
блокирующая ошибка HTML, поиска или Python 3.14, ограничить исследование одним коротким циклом;
резерв — Starlight с теми же Markdown/HTML. Не строить собственный движок как обход ошибки.
Точную версию Zensical выбрать по успешному прогону и записать в lock, не угадывать её в плане.

Каждый этап — самостоятельный небольшой коммит после обязательного gate проекта.
Первая полезная поставка заканчивается на DOC-02; все этапы вместе дают завершённую организацию.
Ориентир по трудозатратам: портал и авторский workflow — 1–2 рабочих дня,
редакционная сверка больших планов и схемы — ещё 1–3 дня. Это оценка, не измеренный срок;
основная неопределённость находится в содержании документов.

## 10. Проверки и границы первой версии

- Чистый checkout, Python 3.14, установка по lock и строгая сборка без ключей и сервисов.
- Сервер слушает `127.0.0.1:8001`; остановка не оставляет фонового процесса.
- Изменение, добавление и удаление Markdown/HTML/CSS корректно отражаются в предпросмотре.
- Главная, меню, оглавление, якоря и три самостоятельных HTML проверены в браузере.
- Есть проверка внутренних ссылок готового HTML; временно вставленная битая ссылка должна
  действительно ломать проверку. Встроенную validation настроить явно, HTML проверить отдельно.
- Удалённый исходник не остаётся в чистой сборке; предупреждения strict исправляются,
  а исключения для прототипных `href="#"` ограничены конкретным прототипом.
- Проверить поиск по русским, польским и техническим словам, клавиатурную навигацию,
  длинные таблицы и код на узком экране.
- После установки зависимостей документация и поиск доступны без интернета. Google Fonts
  заменить системными fallback или локальными файлами; не добавлять CDN ради диаграмм.
- Сборка содержит только документацию и её ресурсы. Исходный код, `.env`, SQLite и дампы
  не копируются в `site/`; внешние ссылки на GitHub требуют интернета и явно отличаются.
- CI выполняет docs-проверки отдельно от тестов бота и web. Публикация в интернет не настраивается.

Настройки каталогов и URL описаны в [Basics](https://zensical.org/docs/setup/basics/),
настройки проверок — в [Validation](https://zensical.org/docs/setup/validation/).
Возможности генератора выше сверены с официальной документацией; проверки на реальном корпусе
перечислены как будущие критерии, а не как уже полученные результаты.
