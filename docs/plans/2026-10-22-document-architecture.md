# План развития обработки документов и истории результатов

Составлен 22 октября 2026; уточняется при реализации. Статус: поэтапная реализация,
выполненные части и их приёмка отмечены в checklist ниже.
Основание: [архитектурный аудит](../reviews/2026-10-22-document-architecture.md).
[Журнал реализации и проверок](2026-10-22-document-architecture-progress.md).
Проверенная при составлении версия: `bb19c248bbbf9e6c0caf876bbc78c32bbe7bd103`.

Цель — сделать путь от официального материала до читательского сообщения воспроизводимым,
а незавершённую работу восстанавливаемой после потери выполняющего процесса и его диска.
Сохранить нынешние продуктовые правила и работающие гарантии, исключить незапланированные
платные LLM-вызовы и измерить накладные расходы хранения/checkpoint. Каждый этап должен
давать самостоятельный проверяемый результат.

Этот документ описывает будущие изменения. Названия новых типов, таблиц, флагов и команд —
предлагаемые контракты, а не уже существующие интерфейсы. Номера SQL-миграций назначаются
при реализации по фактическому концу `MIGRATIONS`; план не резервирует v49 и последующие.
Сохранение плана не означает выполнение миграций, смену deployment или включение новых разборов.

Уточнение владельца 23 октября: исходные материалы занимают гигабайты, поэтому постоянный
архив сырых файлов не выбран как обязательная часть реализации. DA2 сначала сравнивает
объёмы и гарантии разных профилей хранения. До решения не внедрять production blob store
и не связывать остальные улучшения с обязательным сохранением всех оригиналов.
Дополнительное ограничение владельца: по возможности минимизировать рост SQLite-дампа.
Новые сущности и история не оправдывают многократное сохранение одних текстов и snapshot;
компактность проверяется отдельно по [критериям состояния](#compact-state).
Каждый законченный промежуточный результат должен быть deployable и сохранять работу
продукта до следующего этапа. Это обязательный критерий [поставки по частям](#deployable-increments),
а не только требование к финальной версии архитектуры.

## 1. Границы и действующие решения

Сохраняем модульный Python-проект, `uv`, строгую типизацию, существующие source seams,
SQLite, batch-провайдеров и очередь публикаций. Сервисы зависят от портов, моделей и чистых
функций. Сетевые чтения можно распараллеливать, окончательные записи делаются в порядке входа
на вызывающем потоке. Время в сервисах поступает от `Clock`.

Не включаем в обязательную программу микросервисы, Kafka, графовую БД, полное Event Sourcing,
универсальный юридический AST, массовый OCR или автоматический LLM-выбор каждого файла.
Не объединяем RCL, RPW, druk и окончательный акт по похожему названию: действующие официальные
связи и правила продолжения карточки сохраняются.

Текущие инструкции остаются каноническими до внедрения соответствующего этапа:
[наблюдения и доставка](../process-plans.md), [выбор текста](../text-selection.md),
[схема и миграции](../reference/database.md), [retention](../state-retention.md).
Планы [выбора документов](2026-10-17-document-selection.md) и
[проверки комплекта](2026-10-17-document-selection-evidence.md) не запускаются заново:
уже реализованные правила и результаты приёмки становятся исходным контрактом.

### 1.1. Предлагаемые решения для первого прохода

| Вопрос | Решение плана | Когда пересматривать |
| --- | --- | --- |
| Долговечность Telegram | Развить существующий Git checkpoint той же ветки `state`; сохранять намерение до эффекта и исход после | Измеренная стоимость checkpoint мешает срокам или размер dump становится неприемлемым |
| Число writers | Один исполнитель состояния; CAS при любом push, без перезаписи чужого состояния старой локальной базой | Появляется обоснованная потребность в нескольких writers |
| Идентичность файлов | SHA, размер, URL и происхождение сохраняются отдельно от факта хранения байтов | Ссылка на сохранённый объект появляется только при фактическом сохранении |
| Production-хранение | Текущая SQLite и существующие обязательные payload/retention — совместимый начальный режим; S3/другое внешнее хранение отложено | Расширение профиля — отдельное будущее решение по измерениям, не условие остальных выпусков |
| Размер SQLite-дампа | Минимальные метаданные и необходимые payload, ссылки на общее неизменяемое содержимое; измерение до/после каждой миграции | Допустимый прирост задаётся по baseline; обязательные pending/unknown не удаляются ради лимита |
| История результатов | Неизменяемые вычисления и применения, актуальные поля `Bill` как проекция | Удаление старых полей допускается только после полного перехода потребителей |
| Общая очередь задач | Сначала связать существующие механизмы идентификаторами и зависимостями | Выделять общее ядро только после сравнения минимум двух потребителей в DA8 |
| Цитаты основного анализа | Сначала сохраняемый вход и адресуемые блоки; затем отдельная проверка качества DA9 | Новая модель/schema включается только после профильной приёмки |

Остаются два конкретных решения с обязательным результатом, а не бессрочные вопросы:
в DA1 — представление обычного редактирования карточки в существующей очереди;
в DA2 — описание текущего режима, измерения и, только при отдельном решении владельца,
расширение состава/сроков хранения и выбор backend. Пока это решение отложено, текущий режим
достаточен для совместимых выпусков. ADR фиксирует выбранные границы и ограничения;
решать вопрос S3 или другого внешнего хранилища сейчас не требуется.
Постоянный runtime с SQLite на долговечном диске рассматривается в ADR как альтернатива;
перенос на имеющийся VPS не считается автоматически безопасным или уже согласованным.

### 1.2. Профиль хранения выбирается по измерениям

| Вариант | Что сохраняется | Какие гарантии доступны |
| --- | --- | --- |
| Метаданные и решения | SHA/URL/связи, причины выбора, результаты, существующий обязательный pending payload | Аудит решения и восстановление работы; исторический текст по одному SHA не восстанавливается |
| Тексты и точные входы | Предыдущий состав плюс выбранные извлечения/контексты в пределах установленного retention | Проверка сохранённого входа и сравнение сохранённых текстов; новый парсер на старом оригинале без raw не запускается |
| Выборочные оригиналы | Предыдущий состав плюс raw нужных дел/сложных случаев на установленный срок | Повторное извлечение только сохранённых оригиналов, явные exclusions остальных |
| Полный raw-архив | Все скачанные оригиналы и нужные производные в пределах выбранной политики | Наиболее широкий replay, наибольший объём и обязанности backup; не исходный выбор по умолчанию |

Сравнить каждый вариант на реальном потоке: все кандидаты, фактически использованные материалы,
релевантные дела и опубликованные сообщения. Отдельно посчитать уникальные байты, извлечения,
точные входы, scan derivatives, повторный текст в JSON/request, прирост и объекты, закреплённые
старыми backup. Проверить объём до/после сжатия и несколько сроков хранения; дедупликация сама
по себе не доказывает приемлемого размера. Сроки 30/90/365 дней могут быть сценариями оценки,
но не назначаются политикой без результата измерения.

Корпус для исследований и production-хранилище имеют разное назначение. Размер всего корпуса
не является измерением необходимого production-архива. Архитектура идентичностей, единая
политика выбора, точные диапазоны, история результатов и durable delivery полезны при любом
профиле. Обещание offline replay относится только к реально сохранённым данным.
Решение включает квоты и поведение при их достижении: остановить новую архивную запись/зависимую
работу с явной причиной, а не удалять обязательные входы pending/unknown или молча обещать
полное покрытие. Тексты и сериализованные запросы тоже измеряются, а не объявляются дешёвыми заранее.

### 1.3. Инварианты, которые нельзя потерять

- Неопределённая внешняя операция не повторяется автоматически. `dismissed` не означает `sent`.
- Событие и сохранённая физическая доставка имеют разные идентичности; digest membership,
  parent, состав группы, held changes и физические части не пересобираются после попытки.
- Свежие сведения об участии обновляются только до заморозки первой попытки и отдельно
  от исторических стадий и анализа. Историческое исправление использует исходную дату и контекст.
- Оплаченный результат, применение результата и повторное использование — разные записи.
  Переиспользование не создаёт второе списание токенов.
- Смена prompt, экстрактора или политики сама по себе не создаёт новость, платный backfill
  или массовое переосмысление старых карточек.
- Предложение, рекомендация и решение разделены. Файл поправок не является автоматически
  новой сводной редакцией. Дата загрузки не заменяет собственную дату текста.
- Равные байты означают возможность общего хранения, а не равенство юридических документов,
  их роли, редакции или принадлежности делу. Сходство текста не доказывает несущественность.
- Старый snapshot без новых данных остаётся явно legacy/unknown. Отсутствующее наблюдение
  не становится отрицательным фактом, отсутствие доказательства полноты — доказанной неполнотой.
- SQL-миграции append-only; downgrade схемы отсутствует. `pending-batches.json` сохраняется
  вместе с каждым durable snapshot, включая промежуточные checkpoint.

<a id="compact-state"></a>
### 1.4. Компактность SQLite-дампа

SQLite хранит рабочее состояние, идентичности, связи, результаты, небольшие доказательства
и обязательные payload незавершённых операций. Постоянное добавление оригиналов, полных
извлечений/каталогов и диагностических трасс в SQL dump не является выбранным способом архивации.
Если DA2 предусматривает хранение крупных объектов, их backend и backup оцениваются отдельно;
из этого ограничения не следует обязательное создание внешнего хранилища.

- Для одного неизменяемого содержимого — одна запись и ссылки. Новые extraction/input/result/
  content versions не копируют целиком `Bill`, текст или comparison snapshot на каждом шаге.
  Повторная проверка неизменившегося материала ссылается на прежние данные; каждое чтение
  источника не создаёт новую полную версию истории.
- Ссылка может заменить frozen snapshot только на действительно сохранённый неизменяемый
  объект, защищённый теми же pending/unknown/backup обязательствами. Ссылка на текущий `Bill`
  или живой URL не эквивалентна сохранённому историческому snapshot.
- Dual write и legacy JSON на время миграции допустимы, но их пиковый прирост измеряется.
  Для временной избыточности назначаются условие удаления и этап перехода всех потребителей;
  новый baseline не создаётся массовым копированием всей старой истории.
- Подробные traces, повторные наблюдения и временные manifests имеют профильные сроки/лимиты.
  Идентичности публикаций, учёт оплаты, operator audit и необходимые pending dependencies
  сохраняются. Снижение размера не разрешает обрезать frozen payload или uncertain work.
- Измеряются раздельно SQLite, обычный SQL dump, сжатый dump, прирост истории ветки `state`,
  время checkpoint и restore. Сжатие текста/BLOB внутри базы не доказывает уменьшение
  SQL-представления: оценивается фактический результат `dump()` и его сериализация.

Для каждой миграции сравнить один и тот же snapshot до/после, затем одинаковые последовательности:
неизменные повторные прогоны, новые версии, большие batch-входы/сканы, failed/unknown и retention.
Показать прирост на уникальный документ/результат и прогноз по выбранным срокам хранения.
Порог в байтах или процентах определить по измеренному baseline до включения; числовой предел
этим планом пока не назначен. Гарантия жёсткого размера невозможна ценой удаления нужной работы.

<a id="deployable-increments"></a>
### 1.5. Каждый промежуточный выпуск самодостаточен

Этап DA обозначает направление работ; он не равен одному релизу или одному коммиту.
Каждый законченный коммит, предназначенный для `main`, должен запускаться в production
самостоятельно. После его выпуска можно остановить реализацию на недели: обычные discovery,
analysis/collect, tracking, доставка, команды и digest продолжают работать без следующего
DA-этапа, обязательного backfill или нового внешнего сервиса.

Для изменения модели/хранения применяется последовательность совместимых выпусков:

| Выпуск | Изменение | Работающий продукт после остановки на этом выпуске |
| --- | --- | --- |
| A. Расширение | Совместимые модели/nullable defaults, reader старого и нового формата, additive migration | Прежний runtime-путь и сохранённые очереди работают; новые данные ещё не обязательны |
| B. Наблюдение | Новые метаданные или сравнение решений без влияния на выбор и внешние эффекты | Старый путь остаётся рабочим; новый не создаёт второй intent/send/charge |
| C. Один потребитель | Полный вертикальный срез prepare → queue → collect → apply/recovery для одного purpose/вида события | Этот потребитель использует новый путь, остальные — прежний; переходы между ними проверены |
| D. Переключение | Включение принятого нового producer/consumer с сохранением legacy readers/handlers | Новая работа создаётся выбранным путём, прежняя завершается по своему frozen контракту |
| E. Удаление совместимости | Отдельный выпуск после завершения/проверенного переноса старой работы и перехода всех читателей | Нет оставшихся legacy consumers; удаление подтверждено проверкой состояния и rollback-планом |

Это шаблон, а не пять обязательных релизов для каждого helper: независимый чистый перенос
может быть одним выпуском. Частичный перенос без рабочего вызывающего пути, заглушка будущего
consumer или обязательная ручная правка production DB не считаются законченным результатом.

- Существующая конфигурация и старые dumps/JSON остаются допустимыми. Новый необязательный
  механизм сначала имеет безопасный default и не требует немедленно задать новые secrets/vars.
  Обязательная новая граница включается только с готовыми wiring/workflow и проверенной конфигурацией.
- Переключатель управляет созданием новой работы. Формат уже сохранённого batch/request/
  DeliveryPlan определяет его reader и handler; выключение producer не пересобирает pending/
  unknown и не включает повтор через старый sender. Legacy handlers сохраняются до завершения работы.
- Миграция добавляет совместимость до нового writer. Для каждого выпуска указывается точный
  поддерживаемый rollback commit, способный прочитать его состояние; произвольная старая версия
  не считается совместимой. После необратимого внешнего эффекта старый dump не восстанавливается вслепую.
- Bot, relay и poller не обязаны переключаться одновременно. Протокол inbox и polling manifest
  проверяется для реально возможных старых/новых сочетаний; работающий старый job не теряет
  ownership, а single-writer lock/CAS остаётся общим. Новый несовместимый command не выпускается
  из relay до появления совместимого executor.
- Для каждого выпуска проверяются init/restore с прежним state, production-профиль с текущими
  flags, незавершённые batch и frozen delivery обоих форматов, повторный запуск, dump/restore,
  размер дампа и профильный gate. Изменения читательского поведения проходят отдельную приёмку.

В журнале каждого выпуска: исходный/целевой commit, схема и совместимые форматы, новый режим
и defaults, результаты проверок, оставшаяся legacy work, размер state и rollback commit.
Регрессия существующего сценария, потеря работы, повторный send/charge или требование
«доделать следующий этап, чтобы снова заработало» блокируют выпуск.

<a id="progress-tracking"></a>
### 1.6. Отметки выполнения и журнал

Статусы конкретных задач ведутся в checkbox этого плана, факты и доказательства —
в [журнале реализации](2026-10-22-document-architecture-progress.md). Журнал обновляется
после каждого законченного фрагмента до перехода к следующему, а при незавершённой попытке
сохраняет фактический результат и оставшуюся работу. Сохранение плана не закрывает задачи кода.

- Перед началом назвать ID задачи и отметить «в работе» со ссылкой на запись журнала;
  checkbox остаётся `[ ]`. Название этапа DA само по себе не означает начало всех его задач.
- `[x]` ставится только после выполнения критериев конкретного пункта. Рядом — ссылка на
  запись журнала с коммитом и проверками. Частичный результат остаётся `[ ]` с пояснением,
  что сделано и какой критерий ещё не выполнен. Этап не закрывается по одной готовой подзадаче.
- Различать «реализовано локально», «принято», «включено в production», «отложено» и
  «неприменимо». Если критерий задачи требует production-проверки, локальный gate не даёт `[x]`.
  Не требовать deployment для чисто локального подготовительного пункта, если его критерии выполнены.
- Запись содержит дату, ID задачи/выпуска, фактическое изменение, implementation commit,
  выполненные проверки и результаты, migration/форматы/defaults, измерения state, ограничения,
  rollback commit и следующий шаг. Неприменимые поля помечаются явно; результаты не выдумываются
  ради заполнения формы. Для ещё не созданного коммита фиксируется «не зафиксировано».
- Push, CI, deploy и наблюдение production отмечаются отдельными полями с собственным
  доказательством. «Не проверено» не заменяется успехом. Историческое сообщение о тестах,
  результат повторного запуска и вывод из кода обозначаются раздельно.
- Старые записи не переписываются под новый результат: исправление/откат добавляется новой
  записью со ссылкой на прежнюю. Если критерии перестали выполняться, checkbox открывается
  заново с основанием. Отложенный пункт сохраняется в плане, а не исчезает из списка.
- Сам журнал и ссылки обновляются небольшими коммитами; инструкции, числа и детали
  реализации не размножаются между планом и журналом. Перед правками проверять status/diff

## 2. Целевые сущности и их владельцы

Названия обозначают ответственность. Не требуется сразу создавать отдельную таблицу для
каждого типа: небольшие неизменяемые манифесты можно хранить как типизированный JSON.
Адресуемые идентичности, связи, ограничения уникальности и жизненный цикл задаются явно.

| Сущность | Содержимое | Владелец и правило изменения |
| --- | --- | --- |
| `SourceObservation` | Источник, официальный ID/URL, связь с делом, fetched_at, дата источника, snapshot использованных метаданных, blob ref | Source seam; новое наблюдение добавляется, старое не переписывается |
| `ArtifactRef` | SHA исходных байтов, размер, формат, optional storage ref и состояние доступности | Идентичность отдельно от хранения; без storage ref наличие байтов не предполагается |
| `ExtractionResult` | Artifact ref, версия экстрактора и options, части/блоки, координаты, потери и coverage | Экстрактор создаёт новую производную запись |
| `SelectionDecision` | Вопрос, версия политики, все кандидаты и официальные связи, факты, отклонения, выбранный комплект, ограничения | Чистая предметная политика; прежнее решение сохраняется |
| `DocumentEdition` | Адресуемый нормативный комплект/документ, собственная дата и роль, representations и доказанные связи редакций | Предметный слой; дата и название без подтверждающих связей не объединяют редакции |
| `PreparedInput` | Порядок сегментов, исходные диапазоны, преобразования, отбрасывания, scan derivatives, точные контекст и вход | Подготовка анализа; после постановки batch неизменяем |
| `ComputationResult` | Вход, purpose, модель/настройки/schema/prompt, ответ, валидация, оригинальный usage и provider identity | Analysis/review handler; успешный оплаченный результат неизменяем |
| `ResultApplication` | Какой результат и к какому snapshot/generation применён, reused/fresh, время, исход | Сервис применения; `Bill.analysis` и review-поля остаются актуальной проекцией |
| `ContentVersion` | Содержание сообщения, исходные событие/анализ, предыдущая версия, причина исправления | Редакционный слой; отдельно от операций отправки и редактирования |
| `Publication` / `DeliveryPlan` | Канал, физическая часть, exact payload, parent/edit target, состояние попытки и аудит | Существующая очередь; новые ссылки добавляются совместимо |

Логическая цепочка:

<pre>
SourceObservation ──► Artifact ──► Extraction ──► SelectionDecision
        └──────── официальные связи ────────────────┘
SelectionDecision ──► DocumentEdition ──► PreparedInput ──► ComputationResult
ComputationResult ──► ResultApplication ──► событие ──► ContentVersion
ContentVersion ──► существующие Publication / физические части / решения оператора
</pre>

Разделяем три времени: дату документа/события в источнике, время его наблюдения системой
и время анализа/публикации. Поздно обнаруженное старое решение не становится новым решением
только из-за `fetched_at`. Полная bitemporal БД не является предварительным условием.

### 2.1. Идентичности и повторное использование

1. SHA байтов адресует физический объект. SHA извлечения адресует конкретное представление
   текста/блоков. Текущие `text-v2:`/`law-v2:` остаются совместимыми бизнес-отпечатками.
2. Идентичность извлечения включает input SHA, версию реализации, значимые options и версии
   библиотек. Новый экстрактор не заменяет прежнюю производную запись.
3. Идентичность решения включает вопрос, кандидатов, официальные связи и версию политики.
   Файл по новому URL может иметь прежние байты, но другое наблюдение принадлежности.
4. Идентичность запроса фиксирует точный вход, purpose, provider/model/options, prompt и schema.
   Это не автоматическая замена нынешнего memo key: бизнес-политика reuse остаётся отдельной.
5. Идентичность применения включает дело, generation/обработанный snapshot, purpose и результат.
   Повтор одного применения не меняет состояние и не создаёт событие второй раз.
6. Идентичность читательского события не зависит от wording/prompt. Версия содержания и
   ID физической попытки не подменяют identity события.

Перевыполнение LLM не обещает тот же ответ. Воспроизводимость означает возможность проиграть
сохранённый ответ и его применение без нового запроса. Оригинальный usage не обнуляется;
нулевая новая стоимость относится к записи reuse/application и ledger.

**Обязательная fault matrix:**

| Точка сбоя | Восстановление из последнего удалённого snapshot |
| --- | --- |
| До pre-send checkpoint | Telegram не вызван; следующий запуск не утверждает доставку |
| Checkpoint записан, API ещё не вызван | `pending` сохраняется; консервативное `unknown`, без слепого retry |
| Telegram принял, ответ потерян | Сохранённый intent становится/остаётся `unknown`; оператор видит точный payload |
| Локальный `sent`, receipt push не прошёл | Remote pending блокирует повтор; отсутствие локального диска не стирает identity |
| Receipt сохранён, новая часть ещё не начата | Родитель не отправляется снова, потомок использует сохранённый parent |
| Remote tip изменён чужим writer | Нет автоматической перезаписи state и следующих API effects |
| Failed/unknown digest либо revision | Сохраняются membership, original/edit target, части и audit resolutions |
| State push не прошёл после команды | Команда/результат не исчезают из-за независимо опубликованного удаления inbox |

**Проверки:** тестовый remote git repo и fresh `World` восстанавливаются только из remote dump;
локальная DB намеренно теряется. Отдельно обычные exceptions/outage/429, dry-run/no-publish,
single/multipart/group/digest, edits, операторский retry, обе очереди batch.
CLI/wiring/workflow изменения требуют `make test-local-http`.

**Завершение:** ни один reader effect не обходит durable boundary; нет исхода, при котором
потерянный runner разрешает автоматический повтор принятого сообщения. Это не обещание
exactly-once Telegram: неопределённость остаётся явной и разрешается оператором.
Это критерий завершения всего DA1. У промежуточного выпуска новые гарантии относятся только
к уже переведённым потребителям; остальные пути продолжают работать по прежнему контракту.

**Откат:** при сбое остановить новые эффекты, сохранив pending/unknown и удалённый tip.
Использовать код с совместимым чтением очереди. Прежний sender без durable boundary не является
безопасным fallback; восстановление старого dump требует сверки последующих внешних действий.

### 10.3. Переключения и rollback

Для каждого промежуточного выпуска действует [самостоятельный release contract](#deployable-increments).
Таблица ниже описывает отдельные области; она не требует совместного включения всех областей.

| Область | До переключения | После переключения | Безопасный откат |
| --- | --- | --- | --- |
| Durable delivery | До перехода потребителя работает его прежний контракт; новые гарантии ещё не заявляются | Для переведённого потребителя boundary обязателен, включая последующие попытки | Остановка sender или совместимый durable код; не blind resend и не возврат attempted work старому sender |
| Artifact archive | off → record без влияния на решения | Чтение новых exact refs | Legacy fallback только там, где исторический ref отсутствует; повреждённый ref не маскировать |
| Extraction/selection | Сохранение old/candidate decisions параллельно | Новый writer решений для принятого профиля | Совместимый старый policy reader, сохранённые inputs/outcomes |
| Results/content | Dual write, старые проекции читаются | Потребители читают новые refs | Поддерживаемые старые проекции; история не удаляется |
| WorkItem | Один старый handler владеет задачей | Один новый handler владеет мигрированным work | Адаптер legacy с неизменной identity; не параллельный submit |

Новый mandatory state сначала должен читаться rollback-версией либо иметь проверенный
compatibility reader. «Выключить флаг» недостаточно для уже созданных pending/unknown
операций, непотреблённых batch и новых content versions.
Возврат к старому SQL dump без сверки последующих Telegram и LLM действий запрещён:
он может стереть delivery identity и привести к повторной оплате/публикации.

## 6. Критерий завершения программы

Обязательное ядро DA0–DA7 принято, когда для новой карточки/обновления прослеживаются
официальные связи, выбор редакции, версия extraction, идентичность входа, результат,
применение и exact содержание. Потеря runner сохраняет незавершённую внешнюю операцию,
а очистка кэша не уничтожает защищённую историю. Восстановление текстов/входов/оригиналов
обещается только для состава и срока, выбранных в DA2; истечение хранения и legacy-пробелы
видны явно. Постоянный архив всех исходных файлов не является условием завершения программы.

Для каждой включённой source family/purpose сохранены результаты offline и production-приёмки,
а неопробованные классы перечислены явно. DA8 может закончиться обоснованным отказом от общего
ядра; DA9 требует собственного решения о качестве и расходах. Они не блокируют завершение
обязательной архитектурной программы и не дают права автоматически включать paused analyses.

Текущее выполнение видно в checkbox задач, а проверки и включение — в
[журнале реализации](2026-10-22-document-architecture-progress.md).
