# План сокращения дублирования

Дата: 25 сентября 2026. Статус: выполнен локально 26 сентября 2026.
Основание: [аудит версии ff04d9f](../reviews/2026-09-25-duplication.md).

Цель — один источник каждого общего правила при сохранении текущих результатов,
порядка записи состояния, стоимости и поведения при сбоях. Не ставить цель
уменьшить число классов или строк любой ценой. Каждый этап — отдельный небольшой
коммит; push и deployment не входят в этот план.

## Результат реализации

Все восемь этапов завершены. D8 выполнен в предусмотренном ограниченном варианте:
общий backoff, раздельные циклы запросов. Изменения не отправлены в remote.

| Этап | Коммит | Итог |
| --- | --- | --- |
| D7 | `9e02855` | Publishing использует `sources.fetch_print`; локальная копия удалена. |
| D5 | `dd27699` | `adapters.streams.read_bounded` используется Sejm, RCL и Orka; закрытие response и WAF остаются у адаптеров. |
| D4 | `0c2e1ed` | `pricing.estimate_batch_reservation` хранит общую формулу без изменения коэффициентов; подготовленные payload возвращаются прежним ранним выходом. |
| D6 | `f832666` | `services.predecessors.rcl_predecessor` объединяет поиск и NOT_FOLLOWED; неполная запись не становится предшественником. |
| D2 | `fd433bf` | `services.publications.inherit_card` объединяет три пути; второй SQL-вызов сохранён для обновления метаданных существующей публикации. |
| D3 | `ecd2aae` | `analysis_records.RecordFactory` и типизированные usage-поля объединяют сборку четырёх результатов в адаптерах и batch. |
| D1 | `1a8898d` | `services.publications.send_publication` объединяет фиксацию исхода; pending и dispatch остаются у вызывающего сервиса. |
| D8 | `42cb3cb` | `adapters.retries.backoff_delay` задаёт общую задержку для пяти HTTP-адаптеров; контрактные тесты фиксируют число попыток и классификацию ошибок. |

У D6 исходная разница guards не давала разницы результата: `BillLookup._fetch`
проверял наличие `project.rcl` после собственного поиска. Общий resolver переносит
этот guard к поиску. Outage остаётся best-effort и не блокирует сам druk.

У D3 фабрика не получает SDK-ответы и ничего не сохраняет. Проверки типа ответа
остаются в адаптерах. OpenAI передаёт уже нормализованный usage без повторного
вычитания cached tokens; batch использует сохранённую версию промпта. Поля источника,
revision и hash добавляет AnalysisService в прежнем месте, до записи memo.

Контракт D1:

| Путь | До сети | Успех | Обычная ошибка | Outage |
| --- | --- | --- | --- | --- |
| Publishing | Запись/сброс pending у владельца | ID, документы и время | failed, +1 attempt | failed, без attempt, исключение наружу |
| Poster | Сохранённый план и pending у владельца | sent и release только выбранных held changes в одной транзакции | failed, +1 attempt | failed, без attempt, исключение наружу |
| Digest | Собственная pending-запись | ID и время | failed, +1 attempt | failed, без attempt, исключение наружу |

Сетевой вызов остаётся вне транзакции результата. Сохранённые payload/reply_to,
правила допуска к отправке и операторского retry не перенесены в общий helper.
Лог обычной ошибки теперь называет ID публикации, по которому можно найти её в БД.

Для D8 общий runner не введён: RCL выбирает probe timeout и запоминает outage,
Senate допускает отсутствие страницы, Orka распознаёт challenge. Их объединение
потребовало бы дополнительных callbacks/флагов для прежних различий.

При проверке D1 обнаружен отдельный дефект [B55](../BUGS.md#b55): дайджест и черновик
могли повторно отправлять `pending`, `unknown` и `dismissed`. Исправление выделено
в отдельный коммит `5208721`; шесть регрессий падали до изменения и проходят после него.
Неопределённые отправки теперь блокируются до создания pending; replay дайджеста
без сохранённого payload по-прежнему недоступен.

### Выполненные проверки

Перед каждым коммитом кода выполнены полный офлайн pytest, strict mypy, Ruff check,
Ruff format и `git diff --check`. Первый запуск упёрся в запрет sandbox на loopback
CLI-фикстур; весь `test_cli.py` повторён с доступом, последующие полные запуски
выполнялись с этим доступом и прошли.

Добавлены проверки границы потока и закрытия response при успехе/ошибке/лимите;
матрица оценки стоимости; одинаковые сценарии discovery/lookup; alias при конфликте,
повторе и rollback; сохранение старой batch prompt_version после изменения текущей;
матрица исходов трёх отправителей; transport/429/500/404 для пяти HTTP-адаптеров
при нуле и двух повторах. Существующие регрессии доставки, batch, linking, WAF,
probe и workers=1/4 также входят в полный pytest.

`make docs-check` прошёл: строгая сборка, ссылки, якоря, ресурсы и состав портала.
Визуальная проверка документации в браузере не выполнялась. Production state,
внешние API и платные LLM-вызовы для этих изменений не использовались.

## Последовательность

| Этап | Объём | Зависимость | Критерий завершения |
| --- | --- | --- | --- |
| 1 | D7: publishing использует `fetch_print` | Нет | Один helper, прежнее поведение ошибок |
| 2 | D5: bounded stream reader | Нет | Три адаптера используют один цикл чтения |
| 3 | D4: batch reservation estimate | Нет | Одна формула, прежние payload и резерв |
| 4 | D6: resolver RCL-предшественника | Нет | Discovery и lookup используют общий поиск |
| 5 | D2: alias карточки | Нет; удобнее после 4 | Три пути создают alias одной операцией |

Низкорисковые этапы идут первыми, несмотря на высокий приоритет доставки:
самая опасная переделка требует сначала зафиксировать различия её трёх путей.

## Проверки каждого этапа

### 1. Переиспользование `fetch_print`

Удалить локальную копию или оставить тонкую делегацию, если нужен контекст логов.
Проверить успешный print, обычную ошибку с публикацией без PDF и outage, который
останавливает фазу без потери retry budget. Существующая опора:
`tests/scenario/test_outages.py`, `test_joint_bills.py`, `test_tracking_cards.py`.

### 2. Ограниченное чтение потока

Helper принимает iterable байтов, URL и optional limit; HTTP response остаётся
ответственностью адаптера. Проверить пустой поток, ровно limit, превышение на
один байт, несколько chunks, отсутствие лимита, исключение во время чтения.
На уровне адаптеров проверить закрытие response и прежнее распознавание WAF.
Опора: `test_sejm_api.py`, `test_rcl_html.py`, `test_orka.py` в `tests/unit`.

### 3. Резерв batch

Перенести формулу в чистую функцию pricing, не меняя её коэффициенты.
Проверить текст/скан, tokenizer count выше и ниже символьной оценки, None/0,
разные output limits и оба провайдера. Для подготовленного запроса проверить
неизменность `payload_json`, модели, prompt_version и estimated_cost.
Опора: `test_pricing.py`, `test_llm_anthropic.py`, `test_llm_openai.py`,
`tests/scenario/test_secondary_batch_audit.py`.

### 4. Поиск RCL-предшественника

Сначала параметризовать одинаковые сценарии discovery и operator lookup:
локальное совпадение, fallback через RM, отсутствие проекта, NOT_FOLLOWED,
недоступность RCL, неполная запись без `rcl`. Последний случай сейчас имеет
разные guards: явно выбрать контракт и описать, если он меняет поведение.
Сам resolver не создаёт связи, не обновляет summary и не сохраняет baseline.
Опора: `test_rcl_discovery.py`, `test_commands.py`, `test_tracking_rcl.py`.

### 5. Наследование карточки

Ввести сервисную операцию, возвращающую alias. Время передавать от Clock;
операция участвует в транзакции вызывающего кода. Проверить RPW → print,
RCL → print, wykaz → RCL и путь наследования через publishing.
Для каждого — прежние message_id/sent_at/канал, одна карточка, повторный запуск,
существующая целевая публикация, несостоявшаяся исходная отправка, rollback.
Сохранить различия reanalysis, статусов и перерисовки карточки.
Опора: `test_tracking_pre_print.py`, `test_tracking_rcl.py`, `test_wykaz_link.py`,
`test_delivery_checkpoints.py`, `test_joint_bills.py`.

### 6. Сборка LLM-record

Начать с одного вида результата и проверить контракт, затем перенести остальные.
Фабрики разместить в моделях или чистом модуле: не создавать зависимость
services → adapters. Сохранить плоский формат persisted JSON и defaults.
Не объединять реальные HTTP-вызовы и provider-specific prompts.

Проверить все четыре вида результата, Anthropic triage, синхронный и batch-пути,
cached tokens, отсутствующий usage, prompt_version старого batch, source metadata,
ошибочный тип ответа и memo reuse с нулевыми новыми токенами.
Запись memo и изменение статуса должны остаться в исходных транзакциях.
Опора: LLM unit-тесты, `test_secondary_batch.py`, `test_tracking_batch.py`,
`test_batch_reporting.py`, `test_analysis_service.py`.

### 7. Фиксация исхода отправки

Сначала составить контрактную матрицу трёх сервисов; только после этого выделить
общую операцию. Успешный результат должен сохранять и ID сообщения, и документы.
Освобождение held changes выполняется в одной транзакции с фиксацией sent.
Создание плана, eligibility, approval дайджеста и dispatch остаются у владельцев.

Проверить success, обычную ошибку, outage без увеличения attempts, предел попыток,
повтор в одном прогоне, restart, pending → unknown, операторский retry,
сохранённые payload/reply_to и release только included held-change IDs.
Проверки через `World`, fake publisher и состояние публикаций; не вызывать
приватный helper ради тестирования его реализации.
Опора: `test_delivery_recovery.py`, `test_delivery_checkpoints.py`,
`test_process_plans.py`, `test_tracking_outages.py`, `test_digest.py`.

### 8. Retry HTTP

Объединять после параметризованных проверок transport/429/500/404 и закрытия
ответов. Сохранить max_retries как число повторов сверх первой попытки,
backoff, RCL probe timeout и single-attempt, восстановление после outage,
Senate missing_ok, Orka challenge. Telegram отправки в этот рефакторинг не включать.
Опора: `test_http_retries.py` и тесты соответствующих адаптеров.
Если общий runner требует множества специальных параметров, оставить циклы
и ограничиться общей политикой backoff; это допустимый результат этапа.

## Обязательная проверка перед каждым коммитом

Выполнить целевые регрессии, затем проектный gate:

```bash
uv run pytest -q
uv run mypy
uv run ruff check src tests
uv run ruff format src tests
git diff --check
```

При изменении документации дополнительно `make docs-check`.
Если formatter изменил код, проверить соответствующий diff и затронутые проверки.
Сетевые и платные LLM-тесты для структурного рефакторинга не нужны.
Сценарии worker-sensitive обработки должны сохранять одинаковый результат
при workers=1 и workers=4; DB writes остаются на вызывающем потоке.

## Что не входит в работу

Новые функции продукта, изменение промптов/цен/лимитов, миграции схемы,
переотправка сообщений, повторный анализ старых карточек и исправление production
state. Если тест выявит самостоятельный дефект, записать его в `docs/BUGS.md`
и отделить исправление поведения от коммита с сокращением повторов.
