# Выбор документов для законодательных событий

Статус: **план после корпусного аудита**, 17 октября 2026. Проверен `c7a2f19`.
Рабочая логика не изменялась. Добавлены воспроизведения пяти дефектов, исследовательский
replay и доказательства. Production state, Telegram и платные модели не использовались.

## Вывод

Единственного «последнего файла законопроекта» недостаточно. Нужен набор источников,
который отвечает на конкретный вопрос: исходный проект, актуальная редакция проекта,
предложенные поправки, результат голосования или окончательный опубликованный закон.
Файл должен принадлежать нужному процессу, роли и версии, а его извлечение должно
действительно содержать необходимый текст.

Сенатский путь уже проверяет эти условия существенно строже остальных. Его корпусный
replay повторён без потерь. В RCL, вложенных ZIP и основном PDF druku подтверждены
[B97–B101](../BUGS.md#b97). Замена нескольких регулярных выражений не решит всю задачу:
правильный файл можно потерять до проверки содержимого, склеить с чужой версией OSR
или принять обоснование вложенного пакета за сам закон.

2 239 сохранённых процессов иных типов исключены из анализа BILL. Из 23 случаев
зависимости PDF от порядка только 20 относятся к BILL; остальные три — бюджетные отчёты.
136 проектов меняют выбранный набор при перестановке файлов, из них 128 меняют основной
документ. Это **кандидаты на проверку**, а не 128 доказанных ошибочных редакций.
В парах ролей этих 136 проектов 165 сохранённых текстов различаются, одна пара совпадает,
для 14 пар нет обоих текстов. Различие текста не устанавливает, какая версия правильная.

Отсутствие `proposal` у 313 отчётов само по себе не дало нового дефекта: все они являются
отчётами подкомиссий и уже исключены из полного текста. В текущих деревьях не обнаружены
несколько различных `textAfter3` у одного BILL и расхождение порядка полных отчётов с их
датами. Это наблюдения на сохранённых данных, не гарантии будущего API.
Дублирующихся каталогов одной значимой роли в стадии RCL также не обнаружено.

### Воспроизводимость

Из checkout lexinform, без сети, ключей и чтения `.env`:

```bash
uv run --frozen python tools/audit_document_selection.py \
  --corpus ../lexinform-corpus --output /private/tmp/document-selection-new.json
uv run --frozen python tools/replay_senate_documents.py \
  ../lexinform-corpus/sejm/supplements/2026-10-16-senate-resolutions \
  ../lexinform-corpus /private/tmp/senate-selection-new.json
uv run --frozen pytest tests/unit/test_document_selection_audit.py -q
uv run --frozen pytest tests/unit/test_document_selection_audit.py --runxfail -q
```

Последняя команда **должна падать на пяти AssertionError**, пока дефекты открыты.
Обычный запуск: один отрицательный контроль проходит, пять strict xfail.
Метаданные воспроизведений и SHA-256 исходников находятся в
`tests/fixtures/document_selection/`; ZIP-тест — минимальная структурная репродукция
настоящего 712314, а не копия его байтов.

Сохранены [итоговые счётчики и SHA-256 отчётов](../assets/audits/2026-10-17-document-selection/summary.json),
[полный replay метаданных](../assets/audits/2026-10-17-document-selection/replay-final.json.gz)
и [повторный сенатский replay](../assets/audits/2026-10-17-document-selection/senate-replay.json.gz).
Первый отчёт содержит SHA-256 входных JSON. Классификация RCL использует сохранённые
извлечения; только перечисленные выше новые контрпримеры дополнительно проверены по байтам.

## Пять подтверждённых ошибок

### B97: старая редакция и смешанный пакет RCL

UD409 / RCL 12410906: при одинаковом rank выбирается 779502 от 02.06.2026 и старое
обоснование 779503, хотя рядом опубликованы **NOWY TEKST** 791866 от 10.08.2026 и
791867. OSR уже берётся новый, 791873. По исходным DOCX подтверждены разные тексты
закона: 21 197 и 23 264 символа. Это не только смена даты загрузки.
Перестановка файлов меняет решение. Нужна версия пакета с независимой проверкой каждого
компонента; одна сортировка по `created` недостаточна для подписанных копий и приложений.

### B98: соседний ZIP с законом не прочитан

RCL 12390254 / 712314: `PROJ.zip` даёт 8 528 символов обоснования **rozporządzenia**.
`_from_nested` останавливается на этом непустом результате. Следующий `PROJ_UST_zm.zip`
содержит закон и даёт 47 320 символов. Внешний пакет выбран верно, внутренний документ — нет.
Нужен результат извлечения с ролями и происхождением, а не одна строка «что-то прочитано».

### B99: проект rozporządzenia вместо ustawy

RCL 12321775: 418609 (`Projekt rozp ws wykazu stanowisk`) побеждает 418603
(`RM_UD530 na RM`). Исходные Word подтверждают соответственно подзаконный акт и закон.
`_load_text` затем отклоняет regulation, но не возвращается за лежащим рядом законом.
Это пропуск доступного источника, а не доказанный ложный рассказ о самом regulation.

### B100: «za zgodność» ошибочно означает таблицу соответствия

RCL 12400754, стадии 2–4: `W_UST_ZM_PSWiN - zapomogi dla doktorantów - za zgodność.pdf`
исключается широким `zgodno`. Файл 730977 действительно содержит USTAWA и статьи;
в стадии 4 аналогичный файл — 730985. Ошибка скрыта в актуальном конечном снимке
позднейшим ZIP, но воспроизводится на раннем окне консультаций. Запрет таблиц соответствия
нужно сохранить, подтверждая их роль, а не запрещая любой фрагмент слова.

### B101: приложение к бюджету вместо основного druku

VIII/2864: выбирается `2864- trzyletni plan mianowań.pdf`, хотя метаданные содержат
`2864  - ustawa i załączniki.pdf`. Скачанный первый PDF имеет шесть страниц; титул
визуально подтверждает план назначений чиновников 2019–2021, а не законопроект бюджета.
Корпус также содержит разбиение на `c1/c2`, `cz. I/II`, имена с пробелами и префиксом
`druk nr`. Нельзя чинить это только одним новым шаблоном имени.

[Скачанный исходный PDF](../assets/audits/2026-10-17-document-selection/8-2864-selected.pdf)
сохранён без изменения байтов; URL, дата чтения и SHA-256 находятся в итоговых счётчиках.

## Источник для каждого события

| Событие / вопрос | Нужное доказательство | Что нельзя подставлять |
| --- | --- | --- |
| Правительство только объявило инициативу | Метаданные wykaz, явное отсутствие текста | Соседний проект по похожему заголовку |
| Новый RPW / druk | Принадлежащий ему проект и доступное обоснование/OSR; если обнаружен поздно — явно названная актуальная редакция | Письмо, подписи или чужое additionalPrint |
| Новая версия RCL | Полный проект этой версии; согласованные extras | Первый файл в каталоге, новый OSR с прежним проектом |
| Autopoprawka | Отдельный документ изменения + его исходная версия; полный replacement только если подтверждён | Механическая замена основного проекта файлом `-A` |
| Комиссия приложила проект | Полный приложенный текст и решение комиссии | Отчёт подкомиссии, «без поправок», предложение отклонить |
| Поправки II чтения | Дополнительный отчёт / таблица поправок + baseline проекта | Принятие предложений за результат голосования |
| Сейм завершил III чтение | Решение/голоса отдельно; `textAfter3` как принятый на этом этапе текст | PDF голосования как текст закона, старый отчёт как гарантированно принятый текст |
| Сенат внёс поправки | Проверенное постановление, связанное с этой стадией, + предыдущая редакция для сравнения | Проект инициативы Сената, обоснование без операций, предложение сенатской комиссии |
| Сейм рассмотрел поправки Сената | Решение по поправкам и подтверждённая получившаяся редакция; при её отсутствии ограничить выводы | Старый `textAfter3` как окончательный закон; механическое применение всех предложений |
| Вето / повторное голосование | `VetoOutcome` и подтверждённое решение; текст только при доказанной необходимости | Предложение комиссии за окончательный исход |
| Dz.U. / условия применения | Конкретный окончательный текст ELI, публикация и даты отдельно | Анализ проекта как доказательство применимости окончательного закона |
| Итоги консультаций | Позиция участника / ответ органа / новая версия как разные роли с точными ссылками | Публикация мнения как доказательство принятия предложения |

В сохранённых процессах **667 стадий** рассмотрения Сената принимают все или часть поправок
и не несут собственного `textAfter3`. Ранее выбранный `textAfter3` остаётся текстом III чтения.
Это подтверждённый пробел доказательств окончательной редакции, а не измерение 667 неверных
публикаций. До появления проверенного текста допустим рассказ о решении с ограничением;
автоматически собирать окончательный закон из таблиц голосования не предлагается.

## Инварианты будущего решения

1. **Событие задаёт вопрос до выбора файла.** Роль `bill_text`, `amendments`, `decision`,
   `position`, `response`, `final_act` не выводится только из расширения.
2. **Связь важнее сходства названий.** Term, процесс, связанная стадия, druk/RCL ID,
   предмет и версия должны согласоваться. Нечёткое совпадение не даёт разрешения на анализ.
3. **Имя и MIME находят кандидата; содержимое подтверждает роль.** `-A` — контекстная
   подсказка, а не универсальное определение autopoprawka или отчёта комиссии.
4. **Порядок API и ZIP не решает неоднозначность.** Проверять всех равноценных кандидатов;
   равные байты можно объединить, разные нормативные тексты требуют выбора по доказательствам.
5. **Версия состоит из компонентов.** Не смешивать bill/uzasadnienie/OSR разных редакций;
   поздний upload не гарантирует позднюю редакцию, а поздняя стадия может повторять прежний текст.
6. **Проверить основной документ до extras.** Длинное обоснование не делает текстовый слой
   сканированного закона полным. Отказ одного кандидата должен позволять проверить следующий.
7. **Непустое извлечение не означает прочитанный закон.** Отдельно учитывать покрытие страниц,
   нормативный текст, приложения к закону, таблицы, сноски и возможную потерю фрагментов.
8. **Вложенность — часть источника.** Сохранять внешний URL, SHA контейнера, путь/цепочку
   членов, SHA выбранного файла и диапазон страниц/текста. Не приписывать обоснование всему ZIP.
9. **Нормативное приложение остаётся частью закона.** Не отбрасывать его по одному слову
   `załącznik`; приложение к письму тоже может содержать сам проект.
10. **Решение и предлагаемый текст разделены.** Proposal комиссии и операции Сената ещё
    не доказывают принятия Сеймом. Неизвестное решение остаётся неизвестным.
11. **Повторный URL не доказывает прежние байты; новый URL не доказывает новый смысл.**
    Планировать ограниченную перепроверку при свежем source revision; повторный анализ только
    после сравнения прочитанного текста. Не скачивать весь корпус каждый час.
12. **Цена не скрывает потерю доказательств.** Обрезанный текст получает явное ограничение;
    для полного разбора поправок — отложить/разбить с сохранением источников, не заявлять полноту.
13. **Повтор и сбор batch используют тот же источник.** Заморозить выбор, байты/хеши,
    baseline и edit target до отправки; при изменении источника не применять старый ответ молча.
14. **Новые правила не переиздают историю.** Смена селектора/промпта не запускает массовый
    платный переразбор и повторные карточки; для исправлений — отдельный управляемый backfill.

## Архитектурные границы

Предлагаются небольшие расширения действующих портов, последовательно по задачам:

- **Модели и чистые helpers:** вопрос к документу, роль кандидата, связь с событием,
  версия и причины неоднозначности. Результат `selected / waiting / ambiguous / unsupported`
  должен отличать отсутствие текста от невозможности подтвердить его. Добавлять поля с defaults.
- **Адаптеры:** отдают объявленные файлы, байты, формат, структуру Word/PDF/ZIP и качество
  извлечения. Рекурсивный обход архива не решает, что юридически принято или актуально.
- **Источники/сервисы:** строят кандидатов по системе и событию, вызывают чистые проверки,
  применяют правила версии и запрашивают недостающие файлы. Generic analysis/prefilter остаются
  за `TextSource`; правила RCL и Сейма не переносятся в них.
- **Analysis:** получает выбранный пакет и baseline с provenance, считает бюджет и готовит batch.
  Не угадывает документ заново. Непригодный кандидат возвращается с причиной, а не маскируется
  безусловным успешным анализом метаданных.
- **Repository/delivery:** сохраняют принятые доказательства и неизменяемый контекст; worker
  занимается только сетью/извлечением. Порядок записей и результаты workers=1/4 одинаковы.

Не следует объединять всё в один `best_file()` или в универсальный LLM-селектор. Из Senate
переиспользуются provenance, кандидаты и причины остановки; его грамматика постановления
не становится распознавателем проекта, отчёта комиссии или ответа на консультации.

## Порядок изменений и приёмка

Оценки — инженерные рабочие дни, без ожидания внешних API и редакторского решения.
Каждый этап — отдельный проверенный коммит. Сейчас реализован только этап 0.

| Этап | Изменения | Обязательная приёмка | Оценка |
| --- | --- | --- | --- |

| 1. Кандидаты и provenance | Расширить `TextDocument`/результат извлечения; сохранять роли, причины, части и совместимые старые записи | Без смены прежних решений; restore старого dump и batch; SHA, memo keys, исторические edit targets | 1–2 |
| 2. Содержимое архивов | B98: обход соседних ZIP, роли внутренних частей, отказ от «непустой значит закон» | Реальный 712314 + 62 многопакетных кандидата; перестановки ZIP; нормативные приложения; limits/depth; ни одного закона, заменённого обоснованием | 1–2 |

Этапы 2 и 3 зависят от минимальных структур этапа 1. Senate не переписывать в рамках этих
исправлений. Его 701 решения должны сохраняться с теми же URL, 23 PDF оставаться целыми
кандидатами для batch-подтверждения; новые automatic matches подлежат отдельной проверке.

Для каждого меняющего отбор этапа: обычный pytest, целевые регрессии без xfail после исправления,
mypy, Ruff/format, `git diff --check`, corpus before/after и ручная оценка всех изменений.
Инъекции: даты, суммы, отрицания, scope, ссылки, таблицы и приложение к закону; изменение
имени/порядка/контейнера не должно терять текст. Изменение содержания должно оставаться
видимым, включая одинаковый URL. Дополнительно outage без bill-attempt, превышение размера,
неопределённая batch-отправка, restore между submission/collection и workers=1/4.

## Что пока не доказано

- Нестабильность RCL не устанавливает истину для каждого из 128 основных документов;
  не все альтернативы заново извлечены и сопоставлены вручную.
- Старые метаданные druki VIII–IX не обновлялись целиком; свежая загрузка сделана адресно
  для PDF VIII/2864. Основной бюджетный PDF и все его приложения ещё не проверены по байтам.
- Полнота всех комитетских отчётов, additionalPrints и Word footnotes/endnotes в этом
  проходе не доказана. У Word отдельное чтение основного XML не гарантирует чтения всех частей.
- Не доказан реальный случай замены report/after3 по тому же URL. Это подтверждённая
  уязвимость условия `newer`, но до получения пары байтов остаётся гипотезой о данных источника.
- Длинные extras могут скрыть неполное извлечение основного файла; нужен отдельный
  page-level replay, а не вывод из общего числа символов склеенного пакета.
- У 23 сенатских сканов проверены подготовка/целостность входа, а не качество настоящего
  ответа модели. Опубликованные ранее OCR-находки не являются универсальным разрешением OCR.
- Анализы консультаций и ELI не включались. План не отменяет отложенный статус B85/B86/B89/B90
  и не разрешает платный массовый backfill.

## Локальная проверка этого изменения

Полный офлайн pytest прошёл: 2 319 passed и пять ожидаемых xfail, 32 integration/local_http
исключены настройками. Отдельный `--runxfail` воспроизвёл ровно пять AssertionError.
Mypy прошёл для `src`, `tests` и нового audit tool; Ruff, форматирование 291 файла,
`git diff --check` и строгая сборка/проверка ссылок документации прошли.
Повторный replay метаданных сохранил все счётчики и решения. Runtime-код не менялся;
эти проверки не являются оценкой качества настоящих ответов модели или production.
