### 25.5. Данные сайта и протокол полного импорта

#### Постоянные сущности и импортируемые поколения

| Модель | Основные поля / ограничение |
| --- | --- |
| `Matter` | UUID `public_id`, visibility, canonical matter, created_at; не пересоздаётся при импорте |
| `SourceIdentity` | source, external_id, scope, matter; UNIQUE(source, scope, external_id) |
| `MatterRelation` | from/to, kind, evidence_url, decision; различать `continuation`, `joint`, `alternative` |
| `ImportGeneration` | sequence, source_commit, dump_hash, schema_version, contract_version, timestamps, result, counts |
| `ActiveImport` | singleton с FK на последнее принятое поколение |
| `SourceSnapshot` | generation, identity, нормализованный JSON, semantic_hash, успешная проверка; UNIQUE(generation, identity) |
| `MatterFacts` | generation, matter, стадия/даты/оценка для фильтров и текущие ссылки; UNIQUE(generation, matter) |
| `MatterEvent` | стабильный event_key, matter/identity, occurred_at, observed_at, provenance; UNIQUE(event_key) |
| `EventRevision` | event, generation, содержимое/отмена/исправление; история не перезаписывается |
| `MatterContent` | matter + locale, переводимый текст, Wagtail revisions/live state; UNIQUE(matter, locale) |
| `EditorialOverride` | поле, base_hash, proposed value, источник, автор, decision; отдельный слой над фактами |
| `CardRevision` | matter, locale, published_at, фактическое опубликованное объяснение, ссылки на основание |
| `MatterDecision` | merge/split/correction, before/after IDs, основание, автор, время |
| `PublicAlias` | прежний путь/ID → каноническое дело; без циклов |

Scope у Sejm — каденция; у RPW учитывается полный номер с годом. RCL ID не зависит от каденции.
Для Wykaz использовать устойчивый ключ записи, а человекочитаемый `UC104` считать поисковым
алиасом в соответствующей области: совпадение номера в разные годы не доказывает одно дело.
Не использовать nullable term в unique constraint так, чтобы NULL позволял дубли.

RCL → RPW → druk одного проекта сохраняет Matter. Совместное рассмотрение **не означает
тождественность инициатив**: первоначальные Matter остаются, одна карточка показывает группу и
основной правительственный print. Новое внесение после прекращения старого — другое Matter со
связью continuation. Merge/split — отдельная транзакционная операция с аудитом; удаление и
повторное создание строк запрещены. Уже выданные public_id разрешаются и после исправления.

#### Транспорт и порядок

1. Timer раз в 5 минут запускает `import_state`. Advisory lock в PostgreSQL берётся **до** fetch;
   второй импорт заканчивается `already_running`, а не стоит бесконечно в очереди.
2. Получить текущий SHA ветки `state`, затем дамп **именно по SHA**, с timeout и пределом размера
   (первоначально 20 MiB, превышение требует пересмотра лимита). Один fetch не смешивает два commit.
3. Одинаковый SHA/hash уже принят — no-op. Для нового SHA проверить ancestry относительно
   последнего принятого в отдельном bare cache. Предок или переписанная история — остановка и
   запись в очередь оператора; явная процедура rebaseline после аудита. Время commit не порядок.
4. Публичный репозиторий читать без токена. Если доступ станет приватным — отдельный read-only
   credential. Не передавать сайту write-token существующего relay из §24.3.2.
5. Восстановить дамп в одноразовый SQLite в ограниченном subprocess/container: нет сети, секретов
   и mount production volumes; allowlist SQL-операций восстановления, запрет ATTACH/extension,
   лимиты времени/диска. Проверить `integrity_check`, user_version и ожидаемые таблицы.
6. Версия SQLite выше поддерживаемой — предыдущий сайт продолжает работать, импорт сообщает
   несовместимость. Миграции старого дампа выполняются только над временной копией. Импорт не
   вызывает pipeline, LLM, Telegram, discovery или operator commands.
7. Адаптер создаёт типизированный `ImportDocumentV1`: identities, связи, факты, анализ, события,
   успешные публичные Telegram-ссылки, агрегаты охвата. Команды, chat_id техканала, raw errors,
   prompts и потенциальные секреты не проходят allowlist. Сохранять версию контракта даже без API.
8. Валидировать ссылки, даты, FK, дубли, число кандидатов, полноту и резкие изменения. Первоначальный
   guard: падение видимого корпуса более чем на 20% требует сверки; это сигнал, не доказательство
   порчи. Несовместимый контракт или потерянная ссылка — без частичного принятия.
9. Построить новое поколение source snapshots, facts и поисковых документов. Постоянные Matter,
   identities и редакционные данные не заменять. Подготовка выполняется вне длинной транзакции;
   короткая финальная транзакция проверяет предыдущий SHA, сохраняет связи/события/заявки перевода
   и переключает `ActiveImport`. На малом корпусе допустима одна транзакция всех записей после
   разбора; сетевых вызовов внутри неё нет.
10. HTTP-запрос один раз запоминает active generation; facts/search/coverage читаются по нему,
    события — до его sequence включительно. Так даже несколько SELECT не смешают половины разных
    снимков. Неуспешное поколение не доступно посетителям.
11. После commit dispatcher подхватывает сохранённые заявки; `on_commit` может ускорить пробуждение,
    но не является единственным механизмом: процесс может умереть между commit и enqueue.
12. Сохранять последние 10 поколений и не менее 7 суток; удалять только неактивные, неиспользуемые
    служебные снимки после grace-периода. Публичные события, редакции и основания исправлений не
    удаляются этой очисткой.

Повтор полного снимка не создаёт revision, перевод или новое событие, если semantic hash прежний.
Изменение `checked_at` обновляет свежесть, но не `content_updated_at`. Отсутствие строки в новом
дампе не означает отзыва проекта: оставить последний факт, пометить отсутствие в источнике,
отправить на сверку. Операторское скрытие на сайте переживает следующий импорт.

SQL-дамп на сайте — закрытый вход импорта; путь к нему не раздаётся через media/static. Импортируем
все нужные строки для идентичностей, включая `linked`; публикуем дела с пригодным анализом,
учитывая отдельный visibility. Фильтр `status == analyzed` сам по себе потеряет продолжения.
WEB-01 завершён для исторического снимка 16 сентября. Перед фиксацией контракта выполнить
WEB-01r на новой копии state, сохранить отдельный отчёт/fixture с SHA и версией схемы;
`tests/fixtures/website/state_audit_v1.json` не переписывать. Подсчёт повторить перед запуском;
числа §24.2 не являются актуальным launch gate. В контракте отдельно описать pending batch,
`ready_analysis_json`, связанные строки и текущий применённый анализ: незавершённый
результат обработки не должен молча становиться текущим объяснением читателю.

#### Реализованный контракт WEB-03.2 (27 сентября 2026)

`web/src/lexinform_web/ingestion/contract.py` определяет `ImportDocumentV1`.
`projection.project_state` — чистая проекция уже прочитанных и проверенных моделей state;
она не открывает SQLite, не вызывает pipeline, не пишет Django ORM и не публикует страницы.
Получение dump, изоляция восстановления и проверка подлинного SHA/hash — WEB-06.1.
Поколения, semantic hash и атомарная активация — WEB-06.2.

Первый слой WEB-06.1 реализован в `ingestion/restore.py`: дамп восстанавливается в память
после сверки DDL с миграциями; входной DDL не исполняется, SQL-авторизатор допускает только
вставку данных. Проверяются полнота схемы, integrity и внешние ключи, затем соединение
становится query-only. `ingestion.process.restore_in_process` выполняет восстановление
в дочернем Python с пустым окружением, временной директорией, таймаутом и лимитами ресурсов.
Результат проверяется по hash/размеру и открывается только для чтения; временные файлы удаляются
при выходе из контекста. Ограничение памяти процесса действует на Linux, но не заявлено для
macOS. Это ещё не sandbox сети и файловой системы: deployment-контейнер без сети/секретов/
production mounts остаётся отдельным требованием перед приёмом удалённых снимков.

`ingestion.process.project_in_process` восстанавливает SQLite и читает модели внутри того же
ограниченного процесса, возвращая проверенный `ImportDocumentV1` размером не более 20 MiB.
Родитель сверяет origin с переданным pinned SHA и SHA-256 исходных байтов. Адаптер `reader`
проверяет совпадение ключей строк и вложенных identities; повреждённые JSON и потерянные связи
отклоняют документ целиком. Действующий анализ не заменяется staged-результатом; batch intent
`submitting` остаётся unknown. Telegram-ссылки экспортируются только для явно указанного
публичного username и sent-сообщений; без username ссылок нет. PostgreSQL пока не изменяется.

`ingestion.acquisition.acquire_snapshot` уже берёт неблокирующий session advisory lock до
чтения последнего принятого SHA и fetch. `GitSnapshotSource` использует отдельный bare cache,
проверяет ancestry и размер blob, читает `lexinform.sql` по SHA и возвращает hash. Повтор
принятой пары SHA/hash даёт `unchanged`, занятый lock — `already_running`; ошибки не возвращают
старый снимок. Принятым снимок станет только при активации поколения в WEB-06.2: атомарная
проверка прежнего указателя обязательна даже при наличии lock. Git cache требует отдельного
лимита диска: предел 20 MiB относится к blob, а не ко всей скачанной истории.

`ingestion.activation.activate` (WEB-06.2) записывает поколение одной транзакцией под lock графа
identities и row lock `ActiveImport`: тот же SHA/hash — `unchanged`, указатель не равен ожидаемому —
`StaleActivationError` без записей. Строка `ImportGeneration` существует только у принятого поколения.
Цепочка lifecycle получает Matter, который уже есть у любого её звена; цепочка через два Matter —
`ReconciliationRequiredError`. Facts пишутся для канонического Matter, редакционные merge/visibility
не затираются. `content_updated_at` переносится, пока semantic hash (без времени проверки анализа)
прежний. Событие получает новую `EventRevision` только при изменении содержимого; `events_at`
читает ревизии до закреплённого поколения. Пропавшая строка считается в `absent_identities`.

Версия контракта — 1, поддерживаемая нормализованная схема — 35. Старый dump версии
1–35 сначала мигрируется в изолированной копии до 35; обе версии записываются в origin.
Нельзя просто подписать старые строки как normalized_schema=35. Более новая/нулевая схема,
неизвестная версия контракта и дополнительные поля на любом уровне отклоняются.
Повышение схемы требует проверки отображения, а не автоматического расширения allowlist.
Времена сохраняют исходную зону: наивное время API не получает ложный суффикс UTC.
Отсутствующие даты остаются null. Дата обнаружения события не выдаётся за дату его наступления.

Allowlist задаётся явными полями вложенных моделей и явным конструированием проекции.
Нет произвольного JSON payload. Команды/inbox, технические chat_id, delivery snapshots,
raw errors, тексты запросов, prompts, ключи memo и токены не переходят границу.
Документ всё равно является внутренним входом импорта, а не публичным HTTP API.
Ссылки допускают HTTP(S) без credentials/пробелов; это проверка формы, а не разрешение
серверу скачивать произвольный URL. Telegram-ссылки дополнительно ограничены публичными
message URL. Отклоняются дубли identity/event/work keys, потерянные FK и неверные агрегаты.

**Wykaz.** В v34 нет отдельного неизменяемого ID записи gov.pl. Ключ v1 имеет scope
`gov.pl/premier`, external_id `entry:<sha256>` от JSON-массива `[number, published_at,
canonical_url]` (Python `json.dumps(..., ensure_ascii=False)`, UTF-8).
URL нормализуется до HTTPS/www.gov.pl, без query, fragment и конечного `/`.
Исходные номер, дата первой публикации и URL также остаются в `wykaz_evidence`.
Каденция не входит: тот же проект переживает смену Сейма. Sejm использует term+druk,
RCL — global+ID, RPW — global+полный номер с годом.

Такой Wykaz-ключ — идентичность по доступному свидетельству, а не обещание неизменности URL.
При другой URL/первой дате и совпадающем display number WEB-06.2 должен потребовать сверку
с уже известными identities, прежде чем создавать/присоединять новое Matter.
Разные записи с одним номером не объединяются автоматически. Отсутствие свидетельства,
несогласованный номер или повтор одной identity в нескольких строках останавливает проекцию.
Исправление identity выполняется через отдельное редакционное решение WEB-03.1.

v1 фиксирует минимальную проекцию для импорта. Полные деревья файлов RCL, исходные документы,
голоса по депутатам и технические записи не копируются; расширение фактов для UI должно
быть явным изменением контракта с совместимостью и тестами. Полный импорт не восстанавливает
историю из текста Telegram: отсутствие сохранённых событий не означает отсутствие изменений.

### 25.6. Актуальность: необходимая работа в боте до запуска сайта

На 26 сентября в `adapters/sqlite_repo.py::list_tracked` по-прежнему стоит JOIN на `publications` с
`kind='new_bill'`, `status='sent'`, `channel_id`. У `last_checked_at` есть обновление при сохранении
summary. Следовательно, это поле не доказывает, что проверены консультации, вложения и ELI для
каждого импортируемого дела. Это ограничение действующего кода, а не гипотеза о будущем.
`AnalysisRecord.source_checked_at` уже существует и используется при анализе/проверке текста,
но не заменяет проверки process/consultation/act. Отсутствие значений у 93 дел в WEB-01 —
исторический результат, не новое измерение production.

В боте уже реализованы `ObservedProcess`, `BillPlan`, неизменяемый `DeliveryPlan` и checkpoints
наблюдения/доставки — см. [действующую архитектуру](../process-plans.md). WEB-07a расширяет эти
границы, сохраняя processed baseline и атомарность; второй pipeline событий не нужен.
Событие сайта не зависит от успешной отправки в Telegram или редакционного удержания сообщения.
При ожидающем batch факт завершённого наблюдения не подменяется сырым ответом источника:
`awaiting_batch_since` остаётся до checkpoint, неопределённый intent не отправляется повторно.

Для полного A добавить отдельно от переезда PostgreSQL:

1. Append-only SQLite migration: независимый режим наблюдения (`full`, `metadata`, `off`) и
   источник решения; текущие опубликованные дела сохраняют своё поведение. Активные релевантные
   дела сайта получают full, нерелевантные — metadata без повторного платного анализа по расписанию.
   Изменение документа/сферы влияния создаёт задачу пересмотра, не утверждение «не касается навсегда».
2. Отделить запись обнаруженного события от его Telegram-доставки. Все наблюдаемые дела обновляют
   факты/историю; Telegram по-прежнему требует реальной разрешённой публикации и существующего
   thread. Не создавать фиктивный message_id и не снижать порог канала.
3. Проверить весь набор watchers: Sejm, pre-print, RCL, Wykaz, связывание, consultation results,
   agenda, ELI, rollover. Для каждого указать, как наблюдать без thread, и что является успешной
   проверкой. Защита outage/per-bill attempts и порядок записей сохраняются.
4. Записывать успешную проверку по `(source identity, aspect)` — process, consultation, text,
   act; отдельно attempts/outage. Глобальный успешный list-запрос не делает свежей карточку,
   которую источник не вернул. Старую неизвестную свежесть импортировать как unknown.
5. Через `World` доказать: full/metadata без Telegram-card обновляют факты; повтор не создаёт
   события; full c thread сохраняет прежние сообщения; `workers=1/4` эквивалентны. Dry run —
   только копия state, по умолчанию `--max-analyze 0`.

Это обязательная зависимость обещания «актуальные дела сайта», но не перенос хранилища бота.
До её готовности внутренний preview может показывать старые анализы с явной датой и пометкой
«не отслеживается регулярно». Такие записи не попадают в блок открытого участия как проверенные.

Свежесть показывать по источникам. Начальный порог 36 часов применять только к данным, которые
должны регулярно проверяться; объяснять отдельно «бот не выполнил прогон», «импорт отстал» и
«RCL недоступен». У закрытых дел не красить всю историю как ошибку по истечении 36 часов.
Срок истекает по Warsaw time независимо от нового импорта. Для date-only срока хранить точность
и не выдавать вычисленное 23:59 за официальное время; относительный срок от получения письма
показывать как условие, пока нет основания для точной даты.

Открытое окно требует также наступившего начала, отсутствия отмены и подтверждённого способа
участия: одного сравнения `end >= today` недостаточно. Проверить источник времени с секундной
точностью там, где дедлайн задан временем; отдельно тестировать начало, окончание и смену DST.

### 25.7. Перевод, правки и редакторская работа

Разделить три оси состояния: execution (`queued/running/failed/completed`), quality
(`machine/reviewed`) и freshness (`current/stale`). Один enum из §7.2 не позволяет выразить
«проверенный человеком, но устаревший» без потери информации.

`TranslationRequest` хранит entity/locale, source revision/hash, glossary version, статус,
lease/attempt, model, token usage, cost, error code. Уникальность — entity, locale, source hash
и версия явно заказанного перевода. Смена prompt/model/glossary не заказывает массовый перевод
сама. `TranslationResult` неизменяем, ручная правка становится новой редакцией CMS.

Процесс:

1. Взять опубликованную исходную редакцию: для карточек текущий русский анализ + принятые правки,
   для гайда его canonical source revision. Не переводить полный PDF и не строить цепь языков.
2. Подготовить JSON с устойчивыми block ID/field paths. Один документ отправляется целиком с
   glossary и соседним контекстом; IDs, chooser IDs, URL, номера, официальные названия, даты,
   цитаты и польские шаблоны защищены как нетранслируемые поля/placeholder. Для слишком длинного
   гайда — разбиение по разделам с общим контекстом, не молчаливое обрезание.
3. Модель возвращает только текстовые поля по известной схеме. Не давать ей произвольный HTML,
   URL назначения или право менять структуру. Проверять schema, полноту, множества placeholders,
   числа с учётом локального формата, отрицания в тестовом корпусе и термины. Структурная проверка
   не доказывает юридическую точность перевода; пометка machine остаётся.
4. Сохранить результат и стоимость даже если исходник успел измениться. Перед публикацией
   сравнить hash исходной ревизии и версию редактируемого target: старый результат не перезаписывает
   более свежий текст или ручную правку. Создать draft/conflict для сравнения.
5. Если защищённых полей нет и проверки пройдены — публиковать machine-версию с `noindex`.
   Если есть ручные изменения — предложить обновление в draft, сохранить live до решения редактора,
   пометить stale. Существенно устаревшие рекомендации скрыть из блока действий.
6. Reviewer явно отмечает прочитанное `reviewed`, публикует и разрешает индексацию. Исправление
   перевода не меняет официальную стадию и не создаёт Telegram/email event.

Page и snippet используют Wagtail localizations, но `simple_translation` не синхронизирует
последующие правки автоматически. Это соответствует выбранной модели сохранения ручного текста.
[Локализация Wagtail](https://docs.wagtail.org/en/stable/advanced_topics/i18n.html).

Заранее сделать glossary fixtures для всех пяти языков, защищённых польских названий и шаблонов.
Для `be` временный стандарт — официальная орфография из §7.4; это редактируемая настройка редакции.
Интерфейсные `.po` проверяются на пропущенные строки и placeholders в CI, не генерируются на HTTP.
Первичный корпус считать `N × 4`, показать dry-run цену и лимит перед реальным backfill. Один
реальный замер в WEB-09 уточняет бюджет; число $7 из §24 не заменяет usage ledger.

На старте не строить сложный посегментный редактор переводчика: live/draft, пометка защищённых
полей и сравнительный экран достаточны. Внешнюю ссылку на preview для анонимного рецензента
отложить: staff preview с сессией закрывает A без bearer-token в логах и Referer.

### 25.8. Поиск, маршруты, кеширование и индексация

Публичная поисковая проекция `SearchDocument`: entity key, locale, generation для дел / published
revision для CMS, title, Polish title, normalized identifiers, topics, summary/body, visibility,
translation quality. Она строится только из live-контента, обновляется при импорте/публикации и
полностью восстанавливается командой. Черновики, overrides до принятия и feedback туда не входят.

- Ранжирование: точный идентификатор → префикс идентификатора → заголовок → тема → summary → body;
  стабильный tie-break по public_id. Не смешивать число балла с вероятностью совпадения поиска.
- `SearchVector`/`SearchRank` для текста, `pg_trgm` для коротких заголовков/опечаток; `simple`
  как общий предсказуемый старт, `russian`/`english` только после тестовой выборки. `be/uk/pl`
  не получают обещание полноценной морфологии. `Lexeme` нужен лишь при реализованном prefix query.
- Отдельная таблица нормализованных алиасов нужна для `UC104`, `RPW/…`, `druk 3039`, ELI;
  каденция обязательна при неоднозначном druk. Результат объясняет совпадение.
- GET-форма валидирует q/filters/sort/page, ограничивает q до 200 символов, выдаёт 20 строк.
  `q` пустой — каталог; произвольное содержимое пользователя не превращается в raw SQL/tsquery.
- Глобальный `/search/` ищет во всех судьбах дел. Поиск внутри `/bills/` сохраняет явные фильтры;
  при пустом результате предлагает «Искать во всех делах». Не игнорировать выбранный фильтр молча.
- `/b/<uuid>` ведёт на выбор/предпочтение языка через временный redirect; канонический путь
  `/<locale>/bills/<uuid>/<slug>/`. Неправильный slug → один 301. Неизвестный UUID → 404.
  Поддерживать и URL без slug для устойчивых ссылок из бота.
- Материалы имеют общий translation_key и локальные slug. Языковое меню ведёт на эквивалент,
  не всегда на главную. Отсутствующий перевод — честный noindex-экран с доступными версиями;
  удалённая неизвестная страница — 404, а не такой экран.

До измерения нагрузки **не включать full-page cache**: несколько сотен документов обслуживаются
ORM. Разрешены кешируемые фрагменты с ключом `(locale, generation, content revision, template
version)`; TTL для блока действия ограничен ближайшей границей срока, максимум 60 секунд.
Авторизация/preview/формы ошибок — `private, no-store`. Сессии в PostgreSQL; `LocMemCache` допустим
лишь для необязательных вычислений, не для межпроцессных блокировок или rate limit.

Sitemap/canonical/hreflang строить через общий resolver для Django matters и Wagtail Pages.
В sitemap/hreflang включать только существующие индексируемые опубликованные языковые версии;
machine/noindex остаются в меню языка. На страницах поиска и произвольных сочетаниях фильтров —
noindex; редакторские страницы тем имеют собственные canonical. `robots.txt` не закрывает noindex
страницы от чтения директивы. Staging закрыт авторизацией дополнительно к noindex.

SEO snapshots тестировать на пять локалей, старый slug, отсутствующий перевод и объединённое дело.
Статичные OG по языкам использовать из assets, без headless-рендерера в production. Аналитику
подключить только на публичных страницах; запросы поиска, feedback и токены не писать в event data.

### 25.9. Фоновые задачи и расписание

`django.tasks` определяет API, но не запускает worker. Выбранный сторонний backend —
`django-tasks-db`, приложение `django_tasks_db`, `TASKS.default.BACKEND =
"django_tasks_db.DatabaseBackend"`, команда `db_worker`. Старое имя backend из пакета
`django-tasks` не копировать из примеров до его разделения.
[Django Tasks](https://docs.djangoproject.com/en/6.1/topics/tasks/),
[django-tasks-db](https://github.com/RealOrangeOne/django-tasks-db).

Задачи получают только ID записи, source revision и версию payload, не ORM-объекты и не секреты.
Стабильные пути функций сохранять до выполнения/истечения старых заданий; аргументы менять
совместимо. `TranslationRequest` является источником намерения выполнить работу, task backend —
исполнителем. Dispatcher найдёт запрос даже после потери enqueue. Повтор task безопасен за счёт
unique key и сравнения версии перед публикацией.

Worker стартует с параллелизмом 1; импорт работает отдельной короткой management command, чтобы
длинный перевод не блокировал свежесть. После замера разрешить два сетевых перевода одновременно
с отдельными лимитами. HTTP-вызов к LLM имеет ограниченные connect/read/overall timeouts; DB lock
не держится во время вызова. Retry — только временная ошибка, максимум 3 попытки с backoff и
jitter; валидационная ошибка идёт редактору, не в бесконечный цикл.

Нельзя обещать ровно один платный вызов при падении после ответа провайдера: результат мог не
успеть сохраниться. Хранить provider request ID, попытки и стоимость; ограничивать возможную
повторную оплату. При исчерпании месячного бюджета заявки ждут, не теряются.

Обязательные проверки backend в WEB-02: запись задания в транзакции, падение worker после claim,
повторный запуск, зависшая lease, SIGTERM и принудительный SIGKILL, очистка старых task results.
Если backend не возвращает зависшую задачу сам — reconciliation команды переводит только
подтверждённо потерянную попытку в retry; живую задачу не крадёт. Если корректное восстановление
невозможно, выбор backend пересматривается до реализации основной очереди, не обходится
ImmediateBackend в production.

| Timer | Период | Команда / инвариант |
| --- | --- | --- |
| Импорт | 5 минут + небольшой jitter | `import_state`; собственный lock, неизменный SHA — no-op |
| Диспетчер заявок | 1 минута | `dispatch_requests`; lease/dedup, безопасный повтор |
| Отложенная публикация CMS | 1 минута | `publish_scheduled`; один scheduler |
| Проверка здоровья | 5 минут | Web, import/worker heartbeat, очередь, диск, backup age |
| Backup | каждые 12 часов | `backup.sh`; успешность подтверждает внешнее хранилище |
| Обслуживание | ежедневно | `clearsessions`, `prune_db_task_results`, устаревшие временные файлы |
| Проверка индекса | ежедневно | Сверка live-content с поисковой проекцией; repair при расхождении |
| Проверка восстановления | ежемесячно | Изолированная БД/media, smoke, отчёт и длительность |

Timers используют стабильный host wrapper, который читает **active digest** из release state.
Не вшивать вчерашний образ в cron и не запускать scheduler внутри каждого web-контейнера.
Для периодических задач использовать `Persistent=true`, где пропущенный запуск надо догнать;
после простоя один reconciliation, не сотня переводов/рассылок за каждый пропущенный tick.
